# Invoice Lifecycle Management — жизненный цикл инвойса

Инвойс — это не «бумажка с числом», это **финансовый контракт с дедлайнами**, который проходит через 7 состояний. Каждое состояние имеет свои действия. Не отслеживать состояния = терять деньги.

## Prerequisites

- Юрисдикция определена (BY / RU / EU / US)
- Бизнес-форма определена (определяет требования к реквизитам инвойса)
- Подгружены knowledge файлы юрисдикции и бизнес-формы
- Известны реквизиты клиента (название, ИНН/VAT/EIN, юр. адрес)
- Известен договор между сторонами (или его аналог: оферта, заявка)

## Core principle

> **Инвойс — это таймер. С момента отправки начинается обратный отсчёт к деньгам или к потере.** Каждый день без оплаты увеличивает риск.

Многие думают: «выставил инвойс — и жди». На самом деле:
- 30 дней после отправки — обычный режим
- 30-60 дней — нужна напоминалка
- 60-90 дней — собирай документы
- 90+ дней — большая вероятность не получить, нужны решительные действия

Тут **системность бьёт надежду**. Если регулярно работаешь по протоколу, собираешь 90%+ от выставленных счетов. Если работаешь «по настроению» — собираешь 60-70%.

## The procedure

### Step 1 — Подготовить инвойс (drafted)

Перед отправкой проверить:

**Обязательные реквизиты (свои):**
- Название (ООО / ИП / самозанятый / LLC / GmbH...)
- Налоговый ID (УНП BY / ИНН RU / VAT EU / EIN US)
- Банковские реквизиты (для нужной валюты)
- Подписант (ФИО + основание)

**Обязательные реквизиты клиента:**
- Полное название
- Налоговый ID
- Юр. адрес
- (для EU B2B) VAT ID + проверка через VIES если cross-border

**Содержание:**
- Номер инвойса (последовательный, без пропусков)
- Дата выставления
- Дата дедлайна оплаты (обычно invoice_date + 14/30 дней)
- Описание работы (конкретное, не «услуги»)
- Сумма с указанием валюты
- НДС/VAT — отдельной строкой если применимо
- Reference на договор/контракт
- Итого к оплате

**Юрисдикция-специфика:**

| Юрисдикция | Особенность |
|---|---|
| BY | Договор + акт + ТТН (для товаров) обязательны |
| RU | НДС в инвойсе если плательщик НДС |
| EU B2B cross-border | "Reverse charge" пометка, VAT 0% + VIES check |
| EU B2C cross-border | VAT по ставке страны клиента (через OSS) |
| US | Sales tax по штату клиента если applicable |

### Step 2 — Отправить (sent)

Действия:
- Отправить инвойс клиенту (email, Stripe, портал клиента)
- **Получить acknowledgment** — клиент подтвердил получение (email reply, signed copy, или системное событие)
- В БД статус → `sent`, поле `sentAt` = сегодня
- В БД поле `dueDate` = дедлайн оплаты

**Без acknowledgment не считать sent.** «Отправил и забыл» — путь к проблемам через 60 дней («а я не получал»).

### Step 3 — Мониторинг (sent → due_soon → overdue)

Состояния по возрасту:

| Дни до dueDate | Статус | Действие |
|---|---|---|
| > 7 | `sent` | Пассивный мониторинг |
| 3-7 | `due_soon` | Дружелюбное напоминание |
| 0-3 | `due_soon` | Уточнение даты оплаты |
| После dueDate +1 | `overdue` | Жёсткое напоминание |
| `overdue` +14 дней | `escalation` | Эскалация |
| `overdue` +60 дней | `pre-legal` | Подготовка к юридическим действиям |
| `overdue` +90 дней | `write-off candidate` | Решение об отписи |

Мониторинг — **ежедневный** (через scheduler). На утреннем dashboard видны все `due_soon` и `overdue`.

### Step 4 — Collection (общение с просрочкой)

Эскалация **по тону**, не сразу криком:

**Friendly reminder (3-7 дней до due / 1-7 дней после):**

```
Здравствуйте,

Напоминание по инвойсу №<N> от <дата> на сумму <X>. Дедлайн — <dueDate>.

Если оплата уже отправлена — простите за беспокойство, можете отправить копию платёжки?
Если есть какие-то вопросы или нужно перенести срок — давайте обсудим.

С уважением, <Имя>
```

**Firm reminder (overdue +7-14):**

```
Здравствуйте,

Инвойс №<N> просрочен на <X> дней. Оплата на сумму <X> не поступала.

Уточните, пожалуйста, когда ожидать оплату. Если есть проблемы с проведением — давайте найдём решение, чтобы избежать дальнейших задержек.

<Имя>
```

**Escalation (overdue +14-60):**

```
<Контактирует руководитель / финансист, не исполнитель.>

Здравствуйте,

Инвойс №<N> от <дата> просрочен на <X> дней (<XX>+ days по нашим условиям).

Прошу подтвердить дату оплаты или сообщить причины задержки до <деdline +3 рабочих дней>. После этой даты будем вынуждены приостановить работы / передать вопрос в правовой отдел.

<Имя руководителя/финансиста>
```

**Pre-legal (overdue +60):**

```
<От руководителя или юриста.>

<Официальное письмо с угрозой передачи дела в суд / арбитраж.>
<С полной документацией договор+инвойс+акт+претензия.>
```

### Step 5 — Оплата получена (paid)

Действия:
- Подтвердить поступление **по выписке банка**, не по обещаниям клиента
- Сверить сумму (полная / частичная)
- Если полная — статус `paid`, поле `paidAt` = дата поступления
- Если частичная — статус `partially_paid`, поле `paidAmount` = частичная сумма, остаток остаётся overdue
- Отправить клиенту acknowledgment («оплата получена»)
- Выписать **чек / акт выполненных работ** (по требованиям юрисдикции)

### Step 6 — Закрытие (closed)

После полной оплаты:
- Сформировать **акт выполненных работ** (BY/RU обязательно)
- Подписать с клиентом
- В БД статус → `closed`
- Архивировать в Telegram канал (через `archive-publisher`)

### Step 7 — Write-off (если не оплачено)

Если после 90+ дней + правовых действий деньги не получены:
- Принять решение об отписи (обсудить с владельцем)
- В БД статус → `written_off`, поле `writeOffReason` + `writeOffDate`
- В P&L — расходом периода
- В юрисдикции-специфике — может быть налоговый вычет (если есть legal proceedings)

## Worked example

**Сценарий:**
- ООО BY, клиент — нерезидент EU (Germany)
- Инвойс на €5 000 за разработку
- Сегодня: инвойс выставлен 45 дней назад, статус `overdue` +15 дней
- Клиент молчит на 2 friendly reminders

**Решение:**

1. Перевести в статус `escalation`
2. Прислать firm reminder от имени руководителя
3. Назначить deadline: +3 рабочих дня
4. Подготовить документы на случай отказа:
   - Копия подписанного договора
   - Копия инвойса с обоснованием суммы
   - Email-переписка с reminder-ами
   - Распечатка выписки банка (доказательство неполучения)
5. Параллельно — связаться с Legal отделом для оценки sue-ability

В Telegram archive:

```
🚨 Invoice escalation: #2026-045

Client: <DE GmbH>
Amount: €5 000
Days overdue: 15

Status: escalation
Action: firm reminder sent, deadline +3 working days
Backup: договор + инвойс + email-trail подготовлены
Legal: уведомлён для оценки

Next review: <today+3>
```

## Anti-patterns

- **«Я ему сказал, он обещал» как валидное состояние.** Обещания клиентов не меняют статус инвойса. Только реальное поступление денег меняет статус. Учитывать слова — никогда. Учитывать только банковскую выписку.

- **Молчание после reminder.** Если первый reminder не сработал — **обязательно** делать следующий через 7 дней с большей силой тона. Молчание после reminder = «я отказался от долга».

- **Эскалация сразу с криком.** Если первое communication — уже агрессивное, клиент уходит в защитную позицию. Эскалация по уровням, не «сразу в суд».

- **Не закрытый акт после оплаты.** Деньги получены, но акт не подписан. Это **юридически открытая транзакция** — клиент может потом потребовать вернуть («не выполнено»). После каждой оплаты — обязательно акт.

- **Игнорирование частичной оплаты.** Клиент оплатил 70% и молчит. Многие считают «ну ок, и хорошо». Нет: остаток 30% — это **отдельный долг**, который нужно отслеживать тем же протоколом.

- **Write-off без попытки сбора.** Списывать долг через 90 дней «потому что лень разбираться» — это создаёт паттерн «нашему клиенту можно не платить». Если списываешь — то после реальных попыток.

- **Bulk инвойсинг без индивидуальной проверки реквизитов.** Тиражировать один шаблон на 50 клиентов с просто заменой имени — путь к 5-10 неоплате из-за неверного VAT ID, ошибок в адресе и т.д.

## When NOT to use this skill

- Когда речь о **прогнозе** будущих инвойсов — это `cashflow-forecasting`
- Когда речь об **unit economics** — это `unit-economics-calculation`
- Когда речь о **MRR/ARR подписки** — это `mrr-arr-reporting`
- Когда инвойс — это **юридический спор** (отказ клиента, мошенничество) — это Legal

## Integration with finance

Tier 1 скилл — загружается всегда. Особенно при командах `/finance-invoice`, `/invoice`, `/pay`, при упоминании клиентов с долгами.

Использует:
- `db.invoice` — основная таблица
- `db.invoiceHistory` — для tracking изменений статуса
- `lib/archive-publisher` — для публикации значимых событий

Связь с метрикой: точность работы скилла отражается в `overdue-invoice-ratio` (вторичная метрика отдела).
