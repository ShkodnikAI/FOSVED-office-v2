# ТЕХНИЧКА — техническая библиотека годноты

Постоянный каталог проверенных инструментов и практик с вердиктами. Заведена по слову владельца 28.11.2026 (чат), ведёт диспетчер. Назначение: годнота не теряется между сессиями, и по каждому инструменту сразу видны два ответа — **что заимствовать** и **в какой проект**.

Коды проектов-получателей (используются в записях):
- **МЛГ** — ShkodnikAI/Metalogos- (язык Металогос);
- **FOV2** — ShkodnikAI/FOSVED-office-v2 (офис, этот репозиторий);
- **КОНТУР** — агент-контур диспетчера (скрипты и утилиты вне репозиториев).

## Правила ведения

1. Пополнение: после изучения инструмента (README + независимое покрытие, не только самоотчёты авторов; факты проверены) диспетчер заносит запись. Слово владельца «в ТЕХНИЧКУ» — достаточное основание для записи.
2. Статусы: **ПРИНЯТО** — внедряется или внедрено; **ПИЛОТ** — обкатка идёт; **ГОДЕН К ПИЛОТУ** — ждёт решения владельца; **ОТКЛОНЕНО** — с причиной и условием возврата. Записи не удаляются: отклонённое остаётся с причиной, чтобы не переоткрывать уже проверенное.
3. Обязательные поля записи: Что это / Вердикт / Факты / **Заимствовать → проект** / Что НЕ даёт / Источники / Артефакты.
4. Правило заимствования: исполнитель вправе брать в работу только то, что явно указано в поле «Заимствовать», и только в названный проект. Всё остальное — через отдельное слово владельца.
5. Публичность: репозиторий публичный — в записи идут только факты, уже публичные в issues/PR, и общедоступные ссылки. Приватные детали (стенды, ключи, внутренние пути) в библиотеку не класть.
6. Если записей станет много — разносить по `docs/tehnichka/<slug>.md`, оставляя здесь строку-ссылку на запись.

## 1. Open Code Review (alibaba/open-code-review) — ПРИНЯТО, обкатка

**Вердикт (26.11.2026, пилот).** Пригодна как non-blocking полоса ревью на PR-ах нарядов. Один проход, ориентация на точность (precision-oriented); режим делегирования — ревью выполняет уже оплаченный агент волны по чек-листу делегирования, LLM-ключ не нужен, стоимость прохода нулевая.

**Факты пилота** (ревью смерженного PR #551 FOV2; установка `npm i @alibaba-group/open-code-review`, пилотная версия 1.14.4):
- +3 дефекта на уже аудированном и смерженном PR, 0 ложных срабатываний, ~15–20 минут агент-времени на проход;
- F1/F3 (сбой INSERT в `OutboxPut` роняет NightSlot; гонка blanket-пометки `sent_at`) вынесены в наряд #786 [P1]; F2 (переполнение ночного отчёта) к разбору уже закрыт #588 (B.1) + #734 (A.2) — в наряд не входил;
- 1449 тестов на дефектном дереве зелёные: этот класс ошибок (кросс-файловые контракты, грани цикла доставки) тесты не ловят по построению — полоса закрывает слепую зону мерж-аудита;
- дефект инструмента T1: провайдер диффа молча теряет обычный UTF-8 файл — его нет ни в `reviewable_files`, ни в `excluded_files` (git numstat файл видит). Компенсация — гейт numstat-vs-preview; апстрим-черновик подготовлен, публикует владелец.

**Заимствовать → проект:**
- **FOV2**: `.opencodereview/rule.json` в корень (include-маски обязательны: без них в скоуп попадает 4/11 файлов), гейт полноты numstat-vs-preview, пробная полоса ревью 2–3 волны с ретроспективой по метрикам — наряд #787 [P2];
- **КОНТУР**: паттерн «numstat vs preview» — сверка заявленного скоупа ревью с фактическим диффом перед ревью; применим в любом проекте с агент-ревью как защита от молчаливой потери файлов;
- **МЛГ**: пока ничего — полосы ревью на PR-ах языка нет; завести или нет, решается отдельно.

**Что НЕ даёт:** не ревьюит md/канон-контент (нативно только py/yaml); не гарантирует полноту (один проход, precision-oriented); не заменяет тесты и мерж-аудит; не становится блокирующим гейтом мержа.

**Источники:** https://github.com/alibaba/open-code-review
**Артефакты у диспетчера:** отчёт пилота `ocr-pilot-otchet.docx`, `findings.json`, `ocr-pilot-rule.json`, апстрим-черновик `ocr-upstream-issue-draft.md`.

## 2. Spec-Kit (github/spec-kit) — ГОДЕН К ПИЛОТУ, отложен до слова владельца

**Вердикт (28.11.2026).** Возражение владельца про недельные лимиты к spec-kit не относится: он сам квоту не потребляет — это шаблоны, гейты и артефакты поверх агента, которому и так платится за наряд, расход токенов примерно тот же. Проверяется одним пилотным нарядом без риска для лимитов; решение за владельцем.

**Что это.** Официальный открытый тулкит GitHub для Spec-Driven Development, v1.0 (16.10.2026). specify CLI (Python 3.11+/uv) раскладывает в репо шаблоны; процессы идут слэш-командами внутри агента: constitution → specify → clarify → plan → tasks → implement → converge; отдельные треки: bug-fix (assess → fix → test) и idea assessment (intake → research → define → shape → decide). Каждая фаза кладёт markdown-артефакт в репо, питающий следующую фазу; чек-листы и кросс-артефактный анализ из коробки; 40+ интеграций агентов, включая ключи `generic` и `none` (привязка к конкретному CLI не нужна).

**Факты (независимое покрытие, 16.11).** Одна и та же фича строилась дважды: вольным чатом и полным SDD-циклом. Код равноценен в обоих случаях; разница проявилась через неделю — репо с артефактами всё ещё объясняет «почему именно так», репо без них — только дифф; clarify-гейт поймал ошибку до разрастания. Минус того же автора: на мелких задачах церемония тормозит сильнее, чем помогает.

**Заимствовать → проект:**
- **МЛГ**: идеи persisted-артефактов (спека/план/задачи наряда — файлами в репо, а не только в issue) и clarify-гейта до планирования — в волновую модель; переносимо без самого тулкита;
- **КОНТУР**: сам тулкит — одним пилотным нарядом (полный SDD-цикл одного наряда против обычного пути), с замером накладных.

**Что НЕ даёт:** не гарантирует качество кода (независимо подтверждено); добавляет церемонию, тяжёлую для мелких нарядов; требует Python 3.11+ и uv в рабочем окружении.

**Источники:** https://github.com/github/spec-kit ; https://github.github.io/spec-kit ; независимый разбор: https://medium.com/@wasowski.jarek/github-spec-kit-the-complete-practical-guide-to-spec-driven-development-8285c04a75fd

## 3. jcode (1jehuang/jcode) — ОТКЛОНЕНО

**Вердикт (28.11.2026, решение владельца).** Не подходит: постоянные сбои и недельные лимиты провайдеров — непрерывность и многопоточность быстро выжигают квоту.

**Что это.** Rust-харнес для кодинг-агентов: TUI + разовый `jcode run` + клиент-сервер `serve`/`connect`; swarm — несколько агентов в одном репо под сервер-менеджментом (уведомления о конфликтах «код уехал под ногами», DM/broadcast, агенты сами спавнят под-свармы), пассивная семантическая память, self-dev (агент правит собственный исходник, билдит, тестирует, перезагружает бинарник). 22,0k звёзд, 2,6k форков, v1.1.2 (23.11.2026), MIT.

**Разбор отклонения.** «Десятки агентов за ~3,3 МБ ОЗУ на сессию» — это про ресурсы машины, а не про квоты моделей: все свармы едят из тех же подписок Claude/OpenAI по OAuth (5-часовые окна плюс недельные потолки). Сварма из 8–10 агентов выжигает недельную квоту за час-два, дальше деградация и сбои, которые выглядят как глюки харнеса, а на деле — упор в лимит провайдера. Дополнительные оговорки: бенчмарки самопубликованные (часть повторных прогонов на dev-сборке); ~268 открытых issues по состоянию на август (v0.75); установка `curl | bash`; работа с платными OAuth-кредами — только в песочнице.

**Условие возврата из архива:** переход на API-биллинг (pay-per-token, без недельных потолков) — тогда пересмотреть как производственный контур для уплотнения волн.

**Заимствовать → проект:** сейчас нечего.
**Что НЕ даёт:** не методология (сама по себе агентов не учит писать); проблему квот не решает, только делает расход наглядным.

**Источники:** https://github.com/1jehuang/jcode ; https://jcode.sh ; разбор: https://explainx.ai/blog/jcode-agent-harness-swarm-memory-performance-july-2026 ; профиль: https://www.ycombinator.com/companies/jcode
