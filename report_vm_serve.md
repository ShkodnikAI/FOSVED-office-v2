## Главный вывод по категории 1

**88 «дубликатов имён» — не коллизии модулей и не инлайн-баг.**

Это **ровно 88 `pattern`, определённых в корневом `app.mlog`**, каждый ровно один раз.

| Проверка | Результат |
|---|---|
| `pattern X(` в `app.mlog` | 88 определений, 88 уникальных имён |
| Внутрифайловые дубли в `app.mlog` | 0 |
| Пересечение списка из аудита с определениями в `app.mlog` | 88 / 88 |
| Имена из списка, которых нет в `app.mlog` | 0 |
| Определения в `app.mlog`, которых нет в списке | 0 |

`InitDB` и `HandleYana` «не найдены во втором файле», потому что **второго определения нет**. Компилятор не показывает два места, потому что второго места нет.

`dept/yana.mlog` и `dept/context.mlog` уже переименованы в `_deprecated_*` и **не импортируются**. Инлайн-гипотеза для этих двух файлов была верной исторически и уже закрыта. Она **не объясняет остальные 86 имён**.

### Что это значит для языка

`mlog check app.mlog --root app.mlog` регистрирует паттерны корневого файла дважды (файл как root + тот же файл как модуль). Это техдолг **Metalogos**, не содержимого FOSVED.

**Не переименовывать 88 паттернов в `app.mlog`.** Это сломает все вызовы из `dept/*` и ничего не даст VM.

Повторить проверку так:

```bash
# контроль: те же 88 имён vs определения
grep -cE '^pattern ' app.mlog

./bin/mlog check app.mlog
./bin/mlog check app.mlog --root app.mlog
```

Если оба режима печатают одни и те же 88 duplicate — баг чекера подтверждён двумя командами.

`HandleDev`/`HandleDesign` удалить из шимов, когда включат импорты отделов.
