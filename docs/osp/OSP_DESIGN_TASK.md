## 2. Замысел ОСП (кратко)

Отдел стратегического планирования: препарирует сложные ситуации (5 уровней: листья → ветви → ствол → корни → плоды), считает потенциал акторов `P = A×R×S×L×E×E_mod`, строит две траектории в точках развилки, даёт калиброванные вероятности (шкала Кента), метки `[ФАКТ]/[ИНТЕРПРЕТАЦИЯ]/[СПЕКУЛЯЦИЯ]`, индикаторы с окнами проверки, premortem, ACH ≥5 гипотез.

Ключевое обещание — **учиться на своих ошибках**: каждый прогноз архивируется, проходит жизненный цикл `drafted → published → watching → verified/missed/partial/superseded`, по наступлении даты проверяется, считается Brier, раз в месяц — рекалибровка (калибровочная кривая, кластеры ошибок, 1–2 улучшения), реже — пересмотр методики. Цели Brier: год 1 ≤ 0.25, год 2 ≤ 0.20, год 3 ≤ 0.18.

## 3. Что реально есть (аудит 01.11 — перепроверь)

- фильтр прямых инвестсоветов.

**Не работает (контур обучения разомкнут):**
- `OSPDraftAnalysis` пишет в `analysis` только тему/режим/статус и только для deep/full; `full_result`, вероятности, индикаторы, `verification_date` не пишутся; обычные запросы не архивируются;
- статус никогда не меняется (нет ни одного `UPDATE analysis SET status`);
- `/osp verify` ищет `published/watching` → всегда «нет анализов»;
- `OSPComputeBrier`, `OSPComputePotential` не вызываются; `analysis_verifications` никто не пишет → `/osp score` всегда «Avg Brier N/A», дальше LLM сочиняет;
- 12 «гейтов качества» `OSPCheckQualityGates` — поиск слов в тексте, два всегда `true`, результат только в журнал (профиль утверждает «BLOCKER»);
- `/osp watch` пишет строку без порогов/окна/связи с анализом; ежедневного обхода `watchlist_scenarios` нет (плановый `control-check` читает `system_settings control_*`);
- `/osp recalibrate`: `INSERT … to_char(datetime('now'),'YYYY-MM')` — `to_char` не существует в SQLite, запись всегда молча падает;

- `dept/visual.mlog` читает `analysis.full_result` для визуализаций ОСП — поле всегда пустое.

## 4. Что известно о точности прогнозов LLM (2025–2026)

Разбор победителей турниров ботов Metaculus FutureEval и ForecastBench (EA Forum «AI Forecasting in 2026: What 11 Analyses Say»; FRI «LLMs Are Closing the Gap…»):

- лучшие LLM отстают от суперпрогнозистов на ~0.017–0.02 Brier, паритет ожидается ~ноябрь 2026;
- **помогает (по силе):** ансамбль 3–7 независимых прогонов (лучше разных семейств моделей), итог — среднее (86% победителей); агентный итеративный поиск, несколько источников; калибровка после прогноза — Platt (~−0.016) и ограничение крайних значений; явная базовая частота; поиск похожих уже разрешённых вопросов; многошаговость (исследование → прогноз → критика → агрегация, ~28 вызовов у победителей); сверка с рынком предсказаний и разбор при расхождении (~−0.01);
- **не помогает / вредит:** «мульти‑персоны»; промпты со словами «Bayesian»; подстройка под мнение толпы; бэктест на событиях, которые модель уже знает (утечка).

Методики, которых нет среди 24 скиллов: Key Assumptions Check, Deception Detection, центр тяжести по Стрейнджу (CG→CC→CR→CV), PMESII‑PT, Cross‑Impact Matrix / Cross‑Impact Balance, условные деревья прогнозов (FRI), Contrasting Narratives / Red Hat. Источники: NATO AltA Handbook, UK MoD Red Teaming Handbook.

Образцы (изучить идеи, код не копировать): `Metaculus/forecasting-tools` (MIT), `ralfboltshauser/open-superforecaster` (MIT — параллельные исследователи, среднее как итог, медиана и logit‑пул хранятся для сравнения, Platt включается **только если улучшает Brier на отложенной выборке**, аудит отклонения от базовой частоты и рынка, карантин источников после даты прогноза), `pmxt` (MIT — единый API к Polymarket/Kalshi/Metaculus и др.), `Blevene/structured-analysis-skill` (Apache‑2.0 — SAT‑техники как Markdown‑скиллы), PyCIB.

Идея владельца, которую нужно проработать: ОСП параллельно прогнозирует **открытые вопросы Metaculus/ForecastBench**, которые разрешаются за недели, — тогда через 1–2 месяца появляется настоящий Brier, калибровочная кривая и данные о том, какие скиллы реально помогают.

## 5. Ограничения

1. **Язык — Metalogos `.mlog`, рантайм v0.38.0** (офис переходит с 0.34.1 нарядом FOSVED-office-v2#620). С 0.36: `http_post`, `send_message`, `exec` и др. требуют `profile capability { allow_carrier: "…" }` или гранта `builtin:<name>`; с 0.38 `cron_run` требует мандат человека. Проверка: `mlog check <entry> --root <entry>`; VM — единственный исполнитель, TW — оракул в CI.
2. **Идентичность Metalogos** (`AGENTS.md` §2): семь опор — `Entity / Pattern / Flow / Memory / Rule / Learn / Adapt`, плюс `Fluid`‑значения с уверенностью (ADR‑0006 — обученная модель как источник уверенности для `Fluid`). Решение «как в Python, только синтаксис другой» — обёртка, а не решение. Признак элегантности — новая способность получается из уже существующих опор.
3. **Безопасность Metalogos:** метки и стоки — вывод LLM `Private`, `redact(...)` перед выдачей; секреты не уходят в ответ; деструктивный SQL — только `db_execute_with_grant`. Не обходить гейты — проектировать с ними.
4. **БД — SQLite.** Миграции — через `AlterColIfMissing` (идемпотентно, см. наряд #612).
5. **Деньги и токены:** ансамбль умножает стоимость. Нужна политика: где ансамбль, где один прогон; бюджет в день.
6. **Честность:** ни одна метрика не должна считаться LLM‑ом там, где её может посчитать программа (Brier, калибровка, hit rate, суммы вероятностей). LLM — для текста и суждений, программа — для чисел и статусов.
7. **Без инвестсоветов** (существующий фильтр сохраняется).
8. **Не ломать:** команды и формат ответов, которыми владелец пользуется сейчас; гейт #469; живой поиск.

## 6. Что нужно от тебя

1. **Центральная идея.** Одна модель, из которой следует всё остальное. Подсказка, которую можно принять или опровергнуть: *прогноз — это сущность с собственным жизненным циклом и уверенностью, а не текст ответа*. Как это выражается опорами Metalogos (`Entity` для прогноза и его исходов, `Rule` для переходов статуса и гейтов, `Memory` для архива и похожих вопросов, `Learn`/`Adapt` для калибровки, `Fluid` для вероятности, которая сама знает свою калибровку)? Что из этого язык уже умеет, а что — нет (тогда это заявка в Metalogos, отдельным списком).
2. **Сквозной поток** от вопроса владельца до записи в калибровочной кривой: карточка вопроса (критерий исхода, дата, «на момент») → исследование → базовая частота → ансамбль → агрегация → ограничение крайних значений → сверка с рынком → гейты → архив → наблюдение → проверка → Brier → рекалибровка. Диаграмма + где каждое звено живёт в коде.
3. **Модель данных:** таблицы/поля (миграция от текущих `analysis`, `analysis_verifications`, `watchlist_scenarios` — не с нуля), инварианты, что считается программой.
4. **Гейты:** какие блокирующие, какие предупреждения, как их проверять не поиском слов (структурированный вывод модели? схема?), что происходит при провале.
5. **Калибровка:** как и когда включается Platt (условие на отложенной выборке), как считаются калибровочная кривая и hit rate, как метрики попадают в `/osp score`.
6. **Тренировочный поток** Metaculus/ForecastBench: как берутся вопросы, как не допустить утечки (вопрос с известным исходом), как отделить тренировочные прогнозы от прогнозов владельцу в метриках, сколько это стоит.
7. **Новые методики:** какие из списка §4 добавить и в каком виде (скилл‑промпт или структура данных — например, условное дерево как `Entity`, а не абзац текста). Что убрать из текущих скиллов.
8. **Примеры кода `.mlog`** (3–5 штук, компилируемых по замыслу, со ссылкой на реальные builtins из `registry.rs`): сущность прогноза, правило перехода статуса, программный Brier + калибровка, ансамбль со средним и ограничением, ежедневный обход наблюдения.
9. **Сквозной пример:** один реальный вопрос (например, «Будет ли ключевая ставка ФРС на конец 2026 ниже 3.5%?») — как он проходит весь поток, какие записи появляются в БД на каждом шаге, что видит владелец в Telegram, что происходит в день проверки.
10. **План:** 3–4 волны нарядов в порядке зависимостей, у каждого — «сделано, когда» (проверяемый критерий, тест‑мутация), оценка стоимости токенов.
11. **Компромиссы и отвергнутые варианты** — что ты рассматривал и почему отказался.

## 7. Критерии элегантности (как будет оцениваться)

- Меньше новых понятий, больше следствий из одного. Если решение требует 15 новых таблиц — скорее всего, идея не найдена.
- Числа считает программа, слова пишет модель.
- Каждое обещание отдела («учится», «калиброван», «Brier ≤ 0.25») проверяется запросом к БД или тестом, а не текстом.
- Существующие сильные части (гейт #469, живой поиск, скиллы) переиспользуются, а не переписываются.
- Работает в рамках гейтов Metalogos 0.38, а не вокруг них.
- Через 2 месяца после внедрения владелец может открыть `/osp score` и увидеть настоящий Brier по ≥50 разрешённым прогнозам.
