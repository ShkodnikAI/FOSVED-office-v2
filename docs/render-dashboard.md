## Native cron Metalogos (наряд №419, 2026-09-21) — целевая архитектура

Планировщик офиса = **нативный cron Metalogos 0.21.0** (наряд №418: дедуп окон,
catch-up `run_once|skip`, per-job IANA TZ, payload-контракт, рестарт-персистность
через KV-стор `data/metalogos_kv.db`). Внешний cron-job.org выводится из
исполнения; keep-alive (бодрствование free-инстанса Render) — waker на
GitHub Actions в публичном Metalogos- (наряд №420; с 2026-09-23 —
`.github/workflows/waker.yml` репозитория Metalogos-, FO-051), потому что
нативный тик не генерирует входящий трафик и не считает время мёртвого
контейнера.

**Реестр заданий владельца (SSOT): `dept/schedules.mlog`** — «внесение задания =
правка файла → деплой → бутстрап перерегистрирует стор идемпотентно по target».
Новые записи по умолчанию `enabled: false` — владелец включает сознательно.
Разовые задания — записи с `at: <epoch>` (регистрируются через `remind`,
доставка в `ReminderCheck`); recipe расчёта epoch — в README-runbook.
Живая поверхность (без рестарта): `/schedules/list`, `/schedules/bootstrap`,
`/schedules/create`, `/schedules/remove` — та же CRON_SECRET-авторизация, что
у `/cron/*`. №426: `GET /schedules/list|bootstrap` также экспонированы через
публичный прокси (секрет в query, `--data-urlencode` по уроку №425) — владелец
может живьём проверить реестр и перерегистрировать его без рестарта;
create/remove остаются mlog-internal (админ-домен).

**Целевой расклад нативных заданий (tz Europe/Moscow, времена MSK wall-clock):**

**HTTP-фолбэк (п.4 наряда):** все `/cron/*`-роуты остаются ручным/аварийным
триггером; дедуп окон №418 делает двойной запуск (HTTP + нативный тик в одном
окне) безопасным. На легаси-пути (см. ниже) внешние cron-job.org продолжают
быть исполнителем без изменений.

**Статус перехода (честно, наряд №419):** прод остаётся на бинаре 0.19.0 —
Category A аудит app.mlog на 0.21 блокирует бут: долг №327
(UNTRUSTED_DECISION, антиинъекция) — ~430 сайтов диалогового контура, плюс
33 деструктивных SQL-сайта без грант-контура (№390) и clearance-хвост
(SECRET_EGRESS_NETWORK 30, UNTRUSTED_EGRESS_NETWORK 35, TAINT_PERSISTENCE 14 —
уже advisory под мостом ADR-0161, который на 0.21 добавит миграционный наряд).
`entrypoint.sh` держит **guard-пробу**: кандидат `bin/mlog-021` проходит аудит →
прод автоматически режется на 0.21 (+ env-allowlist №259, бутстрап реестра,
`METALOGOS_SERVE_BACKEND=interpreter` — VM-хендлеры 0.21 не видят db_decl
соединение, находка №419); не проходит → громкий лог и fallback `./bin/mlog`.
Откат — env-строкой (`MLOG_BIN=./bin/mlog`), `MLOG_BIN_FORCE=1` — форс-режим.
Стейджинг FO-050 доказал нативный цикл на 0.21: бутстрап 7×ADD → рестарт →
стор персистентен (7 заданий) → ре-бутстрап KEEP×7 без дублей; `next_run`
в TZ задания (07:25 MSK = +03:00); create/remove поверх стора без рестарта.

**Наблюдаемые апстрим-находки №419 (кандидаты в Metalogos-наряды):**
1. `cron_add` штампует id секундным таймстампом — батч-регистрация в одну
   секунду даёт одинаковые id; `cron_remove(id)` тогда сносит весь батч.
   Бутстрап №419 обходит двухпроходной схемой (remove → re-add), апстримный
   фикс — наносекунды/счётчик в id.
2. VM-serve (дефолт ADR-0171) не прокидывает db_decl-соединение в хендлеры:
   `[db] Connected` в логе, но любой `query()` в роуте = `no database
   connection` на `METALOGOS_SERVE_BACKEND=vm`; interpreter работает.
3. `init_reminder_persist` никем не вызывается — напоминания (remind) живут
   в памяти и не переживают рестарт вопреки комментарию в коде; реестровые
   one-shot-задания перерегистрируются бутстрапом (past-skip), так что офису
   не мешает.

**Ротация CRON_SECRET (п.5 наряда):** старое значение засветилось на скрине
владельца 2026-09-20. Новое значение сгенерировано и передано владельцу с

## Waker: GitHub Actions keep-alive (наряд №420, 2026-09-22) — финальная архитектура исполнителей

**Итоговая схема:** бизнес-расписания исполняет **нативный cron Metalogos**
(реестр `dept/schedules.mlog`, дедуп окон/catch-up/TZ — №418, бутстрап и живая
поверхность — №419); бодрствование free-инстанса Render обеспечивает **waker на
GitHub Actions** (с 2026-09-23 — `.github/workflows/waker.yml` ПУБЛИЧНОГО
репозитория Metalogos-, FO-051; офисный `keepalive.yml` демонтирован, см.
надгробие ниже) — нативный тик не генерирует входящий трафик и не считает время
мёртвого контейнера. Внешний cron-job.org
выводится из исполнения (cutover-чеклист ниже). Это преемница вердикта #255:
исполнитель расписаний = нативный cron Metalogos; waker = GH Actions.

**Параметры workflow:** schedule `*/10 * * * *` + ручной `workflow_dispatch`;
concurrency-группа `keep-alive` с `cancel-in-progress` (перекрытия пропускаются —
новый пинг отменяет зависший предыдущий); `timeout-minutes: 5`; секретов нет
(`/health` публичен), `permissions: {}`. Шаги: пинг прода
`https://fosved-office-v2.onrender.com/health` — блокирующий (ожидание 200,
`--max-time 120` покрывает холодный старт Render ~50–80 с); пинг стейджинга
`https://fosved-office-v2-staging.onrender.com/health` — неблокирующий
(`continue-on-error`), пока FO-050 активен: стейджинг на free-плане может быть
намеренно спящим/выключенным. Waker НЕ дёргает `/cron/*`-бизнес-маршруты.

**Waker-переезд (2026-09-23, FO-051) — надгробие офисного `keepalive.yml`:**

Парный наряд Metalogos- gh#629 перенёс waker в ПУБЛИЧНЫЙ репозиторий
Metalogos- (`.github/workflows/waker.yml`): GH-hosted `ubuntu-latest` бесплатен
на публичном репо и не зависит от офисной квоты минут (#306). В main
Metalogos- с 2026-09-23, ≥2 успешных прогона с prod `/health → 200`
(runs 35850804764/35850999980). Офисный `.github/workflows/keepalive.yml`
демонтирован (файл удалён) — решено «по месту», без замены:

- **Причина демонтажа:** workflow исполнялся на `runs-on: [self-hosted,
  linux, x64]` — раннер офлайн, ни одного completed-прогона с
  2026-09-22T21:13Z; schedule-тики висели `queued` и снимались
  concurrency-группой следующим тиком (наблюдение 23.09: 06:44Z queued;
  01:45Z/23:36Z/21:13Z cancelled).
- **Почему удаление, а не «оставить `workflow_dispatch`»:** ручной пинг на
  мёртвом self-hosted раннере зависал бы `queued` вечно (зомби-кнопка);
  перевод офисного workflow на GH-hosted — смена биллинг-постуры приватного
  репо, решение владельца (#306), вне границ FO-051. Рабочий ручной пинг —
  `workflow_dispatch` в waker.yml Metalogos- (или curl `/health` с любой

## Наряд №423 (2026-09-22): разбор бут-лога, диагноз 403, решение по CRON_SECRET

**Бут-лог владельца — со старого деплоя.** Все три аномалии в логе
соответствуют формулировкам entrypoint ДО №422: однопопытный бутстрап
(«did not answer» без «after 3 attempts»), version-чек без токена
(«/version: FAIL» — это честный 401), захардкоженный `[e1c8b5a]` в
заголовке. Текущий main (2922c61, №422) эти точки уже закрывает —
после деплоя ожидать новые формулировки.

**Диагноз 403 на `/cron/morning` — доказан пробой на реальном 0.21**
(`scripts/probe021cron.sh` + `probe021cron.mlog`: auth-блок дословно из
app.mlog, 403-ветки различимы). Матрица исходов:

| конфиг | ответ | вывод |
|---|---|---|
| env задан, секрет в URL совпадает | **200 ok** | auth-логика работает |
| env задан, секрет не совпал / не передан | **403 mismatch** | hash-сравнение честное |
| env пуст (переменная не задана) | **403 empty-env** | ветка `cron_secret == ""` |
| CRON_SECRET отсутствует в METALOGOS_ENV_ALLOWLIST | **500 ENV_NOT_PERMITTED** | громкая ошибка в логе, не 403 |

Сопоставление с бут-логом: блок бутстрапа напечатан ⇒ в entrypoint гейт
`[ -n "$CRON_SECRET" ]` прошёл ⇒ переменная в env была НЕ пустая; 500
ENV_NOT_PERMITTED в логе нет ⇒ allowlist был корректный (дефолт entrypoint
включает CRON_SECRET). Единственный согласованный исход — **hash mismatch:
секрет в URL задачи cron-job.org ≠ значению CRON_SECRET в env Render**
(классика — расхождение при вставке, невидимый пробел/перенос).

*(Коррекция №424: вывод «allowlist был корректный» верен только для
CRON_SECRET — живая проба деплоя №423 показала, что
env("INTERNAL_API_TOKEN") в том же процессе ОТКЛОНЯЛСЯ; деталей и фикса —
§№424 ниже.)*

**Действие владельца (синхронизация, ротация не требуется):** открыть
значение `CRON_SECRET` в Render → Environment, заново вставить его в URL
задач cron-job.org (Morning Brief, Admin Reply), сохранив. Затем деплой
tекущего main и наблюдение: `/cron/morning` — 200.

*(Коррекция №425: диагноз «расхождение при вставке» снят — корень в
URL-декодировании query, см. §№425. Переприклейка того же сырого значения
пробу не меняет; владельцу — заменить литеральный `+` секрета на `%2B` в
URL задач, значение в Render не трогать.)*

**Компенсация утечки в логи (№423, без ротации):** werkzeug (dev-сервер
прокси) писал строку запроса целиком — `GET /cron/morning?secret=…` попал в
лог Render. Установлен `QuerySecretMasker` на логгер `werkzeug`:
значения `secret=`/`token=`/`password=`/`api_key=`/`apikey=` в access-логах

каналов нет. История логов Render очищается ретеншеном.

## Наряд №425 (2026-09-22): URL-декодирование query 0.21/Flask — единый корень 403 кронов и «no answer» бутстрапа

**Контекст.** Бут-лог владельца 09:13 (деплой после задания
`METALOGOS_HMAC_KEY` — в логе «METALOGOS_HMAC_KEY loaded from env (32
bytes)», предупреждение №422 ушло): №424-деплой зелёный (`/version: OK`,
`/status ok`), но бутстрап снова «did not answer after 3 attempts» — уже
не гонка холодного старта.

**Ключевое наблюдение.** [try]-ошибки InitDB (duplicate column) в этом
бут-логе всплыли только на `/health` и dry-run — попытки бутстрапа до
InitDB не дошли ⇒ отбивались на auth (403), хотя секрет в URL брался из
ТОГО ЖЕ env, с которым сравнивается. Значит, секрет ломался ПО ПУТИ.

**Корень (подтверждён пробой на реальном бинаре — `scripts/probe021qp.sh`).**
0.21 percent-декодирует значения query — `server.rs url_decode_fallback`,
документированное поведение: `+` → пробел (form-convention), `%XX` →
байты, «a literal `+` must be sent as `%2B`». 0.19 не декодировал —
поэтому до кутовера cron-job.org работал. Следствие: **CRON_SECRET
содержит литеральный `+` (или `%XX`)**, и любой клиент, вставляющий
секрет в URL сырым, получает честный 403. Проба: raw
`?secret=Shkodnik+probe-vto` → **403**; тот же секрет через
`curl -G --data-urlencode` → **200** «bootstrap: KEEP×7 + EXTERNAL».
Диагноз №423 «расхождение при вставке» снят (см. коррекцию в §№423).

**Фиксы (один PR):**
1. `entrypoint.sh`: все три curl с секретом/токеном (бутстрап ×3 попыток,
   version-чек, validation-цикл `/version`) переведены на
   `-G --data-urlencode` — бутстрап самозалечивается при любом значении
   секрета. Гвард — `tests/test_query_secret_compat.py` (ч.1,
   анти-copy-drift) + обновлён `test_schedules_native.py`.
2. `proxy/routes_tail.py`: хелпер `cron_secret_ok()` — все 9 auth-точек
   `/cron/*`/`/scheduler/*` сравнивают декодированное ИЛИ сырое значение
   query. Внутренние вызовы mlog → :4000 с raw `?secret=`
   (NightTickCore/NightTickSlot-цепочки, forge-export, lz-daily)
   перестают тихо 403-иться — раньше `[try]` это глотал, и ночные цепочки
   деградировали до «=FAIL» без аларма.
3. `start_crons.py`: секрет percent-кодируется (`urllib.parse.quote`).
4. README runbook: curl-примеры переведены на `--data-urlencode`.

**Чеклист владельца (замена шага «синхронизация секрета» из чеклиста
№423):** в cron-job.org в URL задач (Morning Brief, Admin Reply) заменить

экспортёр почасовых счётчиков (privacy by design — ТОЛЬКО счётчики и
латентности, содержимое сообщений не читается) → SQLite, retention ≥60 дней;
прогнозист 168ч с квантилями p10/p50/p90; оракул окон (p90(час) > порога ∪
детерминированные слоты). Данные и модель не покидают VM; Render prod — не
платформа инференса. Генератор артефакта — `oracle.py`, дежурный цикл —
ежечасно с догоняющим catch-up (пропуски дозаполняются по курсору).

**Отклонение от буквы наряда (громко):** наряд называет площадкой «VM FO-050»
(стейджинг Render free). Стейджинг не может нести контур: 512MB RAM
(инференс TimesFM не помещается), эфемерный FS (SQLite/retention 60 дней
умирает на каждом рестарте/деплое), плюс гигиена soak FO-050 (чужие процессы
пачкают методику #182). Площадка — приватная VM исполнителя; FO-050 остаётся
чистой soak-площадкой. Требование наряда «данные и модель не покидают VM»
соблюдено.

**Лестница прогнозиста (дух ADR-0165):**
- Ступень 2 (активна): seasonal-naive + эмпирические квантили; история <3
  недель — предписано нарядом.
- Ступень 1 (при ≥21 дне истории и установке пакета): TimesFM **2.5-200m-pytorch**,
  `google/timesfm-2.5-200m-pytorch`, лицензия **Apache-2.0** (проверено живьём
  на HF API: 1.84M загрузок). **TimesFM 3.0 — веса non-commercial, ЗАПРЕЩЕНЫ**
  (рекон владельца 2026-09-23), не пинить. Пин: `timesfm[torch]==2.0.2`
  (requirements VM); пакет 3.0.* не использовать.

**Источники ряда:** (1) waker-прогоны — Actions API публичного Metalogos-
(реальный ряд с первого дня: 6 пингов/час, латентность prod-шага); (2)
собственные /health-пробы prod+staging (ежечасно); (3) детерминированные слоты
`dept/schedules.mlog` (SSOT, только чтение); (4) **owner_activity — ФИД НЕ
ПОДКЛЮЧЁН** (громкий degraded-статус): почасовые счётчики событий владельца
на проде существуют (таймстемпы TG, access-логи), но наружу не торчат. Для
ступени 1 нужен один из: Render API key (логи/метрики) у исполнителя,
log drain, или санкционированный owner-эндпоинт счётчиков — решение владельца.

**Окна v0 (ступень 2, только детерминированные слоты):** 5 ежедневных окон
(04:50–05:05, 07:10–07:30, 09:00–09:15, 11:50–12:05, 20:50–21:05 MSK) + пн
08:50–08:59 (weekly-digest); пинги каждую минуту внутри окна (запас 10 мин на
джиттер GH schedule). Машинный конфиг + cron-строки UTC —
`config/waker_windows.txt` (GENERATED, перегенерируется оракулом).

**Диф wake-часов:** было 24.0 ч/сутки (`'*/10'` 24/7) → стало ~2.6 ч/сутки
(экономия ~89% на ступени 2). Честная цена: сообщение владельца вне окон =
холодный старт ~50 с; слоты исполняются нативным cron в срок (пинг за 10 мин
до слота). На ступени 1 (живой фид) окна расширятся часами реальной
активности p90>порога — латентность интерактива упадёт, экономия
пересчитается отчётом.

**Применение:** правка `.github/workflows/waker.yml` в публичном Metalogos-
— вне границ FO-052 (Metalogos- не трогаем), решение владельца; этот конфиг +
runbook — место исполнения по букве наряда. Еженедельный отчёт «прогноз vs
факт» (MAPE по дням, экономия wake-часов, промахи, ступень) — комментариями
в office#323 (первый — после первой недели контура).
