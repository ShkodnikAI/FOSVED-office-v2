## М1 — Стандарт наряда: гейт качества до постановки в очередь

Каждый пункт — блокирующий; наряд, не прошедший гейт, в очередь не попадает.

1. **Номер и место.** Наряд принадлежит волне реестра §16 плана v2; номер — из номерного пространства волны; публикация не меняет реестр, а исполняет его (§16.0-1). Изменение состава волны — правка плана первой, затем публикация.
2. **Факт с якорями.** Каждый якорь (файл:строка, число, имя символа) проверен на живом снапшоте командой (`grep`/`wc`/`cargo`-вывод); дата снапшота и хэш коммита указаны в тексте. Якоря из памяти запрещены (AGENTS.md §1).
3. **Декомпозиция до файлов.** Раздел «Задача» доведён до перечня затрагиваемых файлов/модулей (§3-файлы); наряд без привязки к коду/документам репо не издаётся.
4. **«Сделано, когда» — только проверяемое.** Каждый пункт воспроизводим аудитором командой/тестом/CI-выводом за ограниченное время без знания контекста; критерии — числа и перечисления, не прилагательные («быстро», «надёжно», «удобно» в критериях запрещены).
5. **Правило №16.0-D — в каждом наряде.** В «Сделано, когда» присутствует пункт: «заглушек нет: grep по `todo!|unimplemented!|SKELETON` в новых файлах — 0, CI blocking зелёный на мерж-коммите».
6. **Границы — громкие.** Ограничение объёма только через loud honest-boundary (прецедент ADR-0125/№241): реальная функциональность заявленного подмножества + явно перечисленный непокрытый остаток. Тихое усечение объёма запрещено и считается невыполнением наряда.
7. **Зависимости и оценка.** «Зависит от / Блокирует» — явные; оценка — диапазон, не точка.
8. **Мета-строка.** Первая строка тела: `> Волна N · план v2 §16.X · Оценка: … · Зависит от: …`.
9. **Дедуп.** Один наряд — одна логическая единица работы; заголовок уникален в очереди; формат заголовка `Наряд №NNN (P*, категория): название`.

## М2 — Протокол отчётности исполнителя

Статусы (Astra-прецедент): `progress` / `verified-wait` / `no-progress`. Шаблон комментария в issue наряда — обязательные поля:

```
[progress|verified-wait|no-progress] Наряд №NNN
Сделано: <факт>
Доказательства: <команда → фактический вывод | ссылка на CI-прогон | ссылка на коммит>
Блокеры: <перечень | нет>
Следующий шаг: <…>
```

Правила:

1. **Каденция:** не реже одного отчёта за рабочий день по активному наряду, если диспатч волны не задаёт иное.
2. **`verified-wait`** = работа завершена, ожидает внешней проверки (CI/ревью/completion-audit); отчёт обязан нести ссылки на доказательства.
3. **Правило трёх:** три `no-progress` подряд → наряд переводится в blocked-audit (М3).
4. **Запрещено:** закрывать issue без пройденного completion-audit (М3); заявлять «готово» без доказательств; переопределять критерии приёмки в отчёте — критерии меняются только правкой плана (§16.0-1).
5. **Вопросы методологии** по конкретному наряду — комментарий в его issue; ответ исследовательской ветки в тот же issue (ролевая граница: ветка не пишет код за исполнителя).

## М3 — Протокол completion-audit и blocked-audit

**Completion-audit** — обязателен перед закрытием любого наряда; проводит исследовательская ветка.

1. По каждому пункту «Сделано, когда»: воспроизвести доказательство на **мерж-коммите** (команда/тест/grep) и зафиксировать фактический вывод в аудите — доказательства, не формулировки.
2. **CI:** blocking-джобы зелёные именно на мерж-коммите ветки наряда (AGENTS.md §8), не на локальном прогоне.
3. **№16.0-D:** grep `todo!|unimplemented!|SKELETON` по файлам, добавленным нарядом, — 0 совпадений.
4. **Границы:** перечисленный в наряде непокрытый остаток совпадает с фактическим состоянием кода; расхождение = возвращение.
5. **Вердикты:** `accepted` · `accepted-with-notes` (перечень notes, у каждого — владелец и срок) · `returned` (перечень несоответствий по пунктам «Сделано, когда»; issue остаётся открытым).
6. **Машинный маркер** первым в комментарии аудита: `<!-- audit: completion №NNN verdict: accepted|accepted-with-notes|returned -->`.

**Blocked-audit** — по правилу трёх `no-progress`.

1. **Классификация root-cause:** устаревший якорь/факт · незакрытая зависимость · неверная оценка объёма · внешнее обстоятельство · конфликт с планом.
2. **Исходы:** устранение блокера → работа продолжается; пересмотр наряда → правка плана первой (§16.0-1), затем переиздание; эскалация владельцу (лейбл `owner-decision`).
3. **Машинный маркер:** `<!-- audit: blocked №NNN class: … outcome: … -->`.

**Общее:** аудитор констатирует соответствие критериям, но не меняет их; спорные вердикты — эскалация владельцу. Каждый аудит — отдельный комментарий в issue наряда.

## М4 — Шаблоны: копируй-и-заполняй-формы М1–М3 (v1.1)

Шаблоны не вводят новых критериев — это формы заполнения М1–М3 и §16.10 плана v2. Правка шаблонов — через правку §21 плана, затем gh#410 (как у всего комплекта). Статусы, форматы машинных маркеров и перечень root-cause'ов фиксированы; менять их нельзя — по ним работают аудит и машинные проверки.

### Ш1 — Наряд (issue-ready; формат `docs/naryad-266-*`)

```
Наряд №NNN (P*, категория): название
> Волна N · план v2 §16.X · Оценка: X–Y д · Зависит от: №MMM | —

**Факт.** <текущее состояние по якорям: файл:строка, имена символов, числа; снапшот <дата> @ <SHA>.>

**Задача.** <что сделать — до перечня затрагиваемых файлов/модулей (§3-файлы).>

**Сделано, когда.**
1. <проверяемый критерий: число/перечисление + воспроизводимая команда/тест>
2. <…>
K. Заглушек нет: grep по `todo!|unimplemented!|SKELETON` в новых файлах — 0, CI blocking зелёный на мерж-коммите (№16.0-D).

**Границы (громко).** Покрыто: <заявленное подмножество>. Не покрыто осознанно: <перечень остатка>.

**Зависимости.** Зависит от: … · Блокирует: …

**Связь.** План v2 §… · ADR-015x (если есть) · диспатч волны gh#…
```

Заполнение: чек-лист М1 (9 пунктов) прогоняется до публикации; якоря проверены командами (`grep`/`wc`/`cargo`) на живом снапшоте — дата и SHA в «Факте»; критерии без прилагательных; оценка — диапазон; номер — из номерного пространства волны §16; заголовок уникален в очереди.

### Ш2 — Отчёт исполнителя (М2)

```
[progress|verified-wait|no-progress] Наряд №NNN
Сделано: <факт>
Доказательства: <команда → фактический вывод | CI-прогон: <ссылка> | коммит: <SHA>>
Блокеры: <перечень | нет>
Следующий шаг: <конкретное действие>
```

Заполнение: каденция ≥1 отчёт/рабочий день; `verified-wait` обязан нести ссылки на доказательства; критерии приёмки не переопределяются (правка — только через план, §16.0-1); три `no-progress` подряд → blocked-audit (Ш4); закрытие issue — только после completion-audit (Ш3).

### Ш3 — Completion-audit (М3; комментарий в issue наряда)

```
<!-- audit: completion №NNN verdict: accepted | accepted-with-notes | returned -->
**Completion-audit · Наряд №NNN** · мерж-коммит <SHA> · <дата>

| «Сделано, когда» | Доказательство (команда → фактический вывод) | ✓/✗ |
|---|---|---|
| п.1 <цитата пункта> | `$ <команда>` → <вывод> | |
| п.K №16.0-D | `$ grep -rn -e 'todo!' -e 'unimplemented!' -e 'SKELETON' <файлы наряда>` → 0 совпадений | |

CI: blocking-джобы зелёные на мерж-коммите <SHA> — <ссылка на прогон>.
Границы: заявленный непокрытый остаток соответствует коду — да/нет (<расхождение>).

**Вердикт:** accepted | accepted-with-notes (notes: <…> — владелец: <…>, срок: <…>) | returned (несоответствия: пп. <…>; issue остаётся открытым)
```

Заполнение: каждое доказательство воспроизводится аудитором на мерж-коммите (не на локальном прогоне); строка п.K обязательна; форма grep с `-e` эквивалентна паттерну М3 (`|`-форма ломает markdown-таблицу); аудитор констатирует соответствие, но не меняет критерии; машинный маркер — первой строкой, без него аудит не засчитывается.

### Ш4 — Blocked-audit (М3; по правилу трёх `no-progress`)

```
<!-- audit: blocked №NNN class: … outcome: … -->
**Blocked-audit · Наряд №NNN** · <дата>
Триггер: три no-progress подряд (отчёты: <ссылки/даты>)
Root-cause: устаревший якорь | незакрытая зависимость | неверная оценка объёма | внешнее обстоятельство | конфликт с планом
Исход: устранение блокера → работа продолжается | пересмотр наряда (правка плана §16.0-1 → переиздание) | эскалация владельцу (лейбл owner-decision)
```

Заполнение: class и outcome — строго из перечней М3; при «конфликт с планом» или эскалации — уведомление владельца в issue диспатча волны.

### Ш5 — Методологический вопрос / ответ (М2 п.5)

```
[методология] Наряд №NNN — <краткая тема>
Пункт наряда: <цитата пункта>
Вопрос: <…>
Контекст: <что уже попробовано; какие якоря задействованы>
```

Ответ исследовательской ветки — в тот же issue с префиксом `[методология-ответ]`: ветка разъясняет наряд и критерии, но не пишет код за исполнителя (ролевая граница).
