# ADR-0004: Каноническая схема таблицы admin_findings — python-вариант

**Статус:** принято (наряд #265, блок A — «решение зафиксировать явно в ADR, не молча»)
**Дата:** 2026-09-20
**Контекст решения:** наряд #265 (аудит #244, слой 1 — подтверждённая потеря данных), верификация двух независимых аудиторов + прямое чтение кода владельцем 2026-09-20

## Контекст

Таблица `admin_findings` создавалась в **двух местах с разными схемами**:

- `app.mlog:108` (и зеркала `dept/app.mlog`, `dogfood_staging.mlog`):
  `(id, severity, file_path, issue, fix_suggestion, status, created_at)`
- `proxy/core.py:395`:
  `(id, severity, category, file, issue, fix, status DEFAULT 'open', created_at)`

Оба места используют `CREATE TABLE IF NOT EXISTS`, поэтому реальную схему
боевой базы определяет порядок бута — та из двух, которая выполнилась первой.
Python-код при этом пишет по одной схеме (`proxy/kg.py:96`,
`proxy/routes_admin.py:1822` — INSERT с `category/file/fix`), а читает по
другой (`proxy/routes_admin.py:1164` — SELECT `file_path`). Когда таблица
создаётся mlog-схемой, INSERT падает (перехватывается и молча уходит в
`error_log` как `data_loss`), а SELECT возвращает ошибку отсутствующей
колонки. Это не гипотеза: конфикт колонок подтверждён двумя независимыми
аудитами и прямым чтением кода.

## Решение

**Канон — python-схема** (`category`, `file`, `fix`, `status DEFAULT 'open'`):

1. Она активно используется живыми python-писателями (`kg.py` — конфликт
   сущностей knowledge_graph; `routes_admin.py` — ночной скан), то есть
   переход на mlog-схему потребовал бы переписывать больше живого кода.
2. Имена `category`/`file`/`fix` точнее по смыслу: писатель из
   `dept/admin.mlog` записывал в `file_path` значение `"dept_activity"` —
   это категория, а не путь к файлу; python-схема даёт для этого отдельную
   колонку `category`.
3. Python-схема содержит осмысленный `DEFAULT 'open'`, mlog-схема — нет.

Изменения по канону:

- `app.mlog`, `dept/app.mlog`, `dogfood_staging.mlog` — CREATE приведён
  к python-списку колонок дословно (как в `proxy/core.py:395`).
- `dept/admin.mlog` — три INSERT'а переписаны на канонические имена
  (`SaveFindings` → `category='code_audit'`; dept-активность →
  `category='dept_activity'`, `file=''`).
- `proxy/routes_admin.py` — SELECT в admin-stats читает `file` (ответ API
  по-прежнему отдаёт ключ `"file"` — контракт с фронтом не менялся).

## Следствия

- Гвард `tests/test_admin_findings_schema.py` фиксирует единство схемы:
  четыре CREATE (3 зеркала mlog + core.py) обязаны иметь идентичный список
  колонок; ни один INSERT/SELECT в коде не вправе упоминать
  `file_path`/`fix_suggestion` применительно к `admin_findings`.
- Данные, уже накопленные в боевой базе под mlog-схемой, этим ADR **не
  затрагиваются**: миграция данных требует явного решения владельца
  (наряд #265 запрещает миграцию без подтверждения — ценность
  существующих записей `admin_findings` нужно оценить по боевой базе
  до пересоздания).
- Другие таблицы с похожим классом расхождения (`facts`, `dialog_history`
  и т.д. по списку аудита #244) — вне этого решения, по правилу «один
  наряд = одна таблица».
