# ADR-0012: Переход боевого бинаря Metalogos с 0.27.0 на 0.27.1 + включение фичи #757 (наряд #399 A.2)

**Статус:** принято (гейты диспатча #403 Wave 3 выполнены: Metalogos- #757
смержен в апстрим `main` PR #759, `260a33a`, и выпущен в теге **v0.27.1**;
office-наряд #401 закрыт до снятия лимита — обязательный порядок соблюдён).
**Дата:** 2026-09-30
**Контекст решения:** наряд #399 A.2 (P0, «обрезка всех отчётов»). Нативный
`call_llm` отделов резал ответы на апстрим-лимите 1024 токена (факт 2026-09-29:
отчёт ОСП «Кадровые перестановки…» оборван, «Вердикт» пуст). Апстрим-релиз
v0.27.1 (PR #759) даёт: настраиваемый `llm { max_tokens: N }` (валидация
громкая на parse; env-фолбэк `METALOGOS_LLM_MAX_TOKENS`; блок-лимиты
зеркалируются в глобальный роутер), видимый `finish_reason` на всех ветках
провайдеров (включая SSE), билтин `llm_last_finish_reason()` (registry 500→501,
typed String), новый дефолт апстрима 4096.

## Решение

**`bin/mlog` = 0.27.1.** Сборка — из официального CI upstream (путь
ADR-0005…0009): workflow «Build and Release» запущен на ref `v0.27.1`
(коммит тега `5b79996`, run 36704203800 — артефакта на теге в момент
исполнения не было, прогон запущен официально через workflow_dispatch;
conclusion=success), артефакт `mlog-linux-x86_64` (34 061 208 байт, ELF
x86-64, sha256 `43fb5c7ad21f8dd9630cf26c548446f29a139209df9d4ba95bd0d4736dbba9b2`).
`mlog --version` → `mlog mlog 0.27.1` (grammar rev: 1).

**Guard-цепочка entrypoint сохранена:** кандидат = `bin/mlog`, проба audit
на аугментированной копии (мост №421), бут-фолбэк = `bin/mlog-020` (0.20.0).
**`bin/mlog-027` вендорен как прошлый-хороший/тест-гвард** (роль mlog-025 из
ADR-0009 переходит к нему); **`bin/mlog-025` выведен из репо** (восстанавливается
из git-истории, прецедент mlog-024). bin/ несёт 0.27.1 + 0.27.0 + 0.20.

**#399 A.2 офисная часть:**
1. `app.mlog` `llm {}`: `max_tokens: 8192` — СРАЗУ ПОСЛЕ providers (грамматика
   0.27.1: хвост блока — упорядоченная цепочка; поле перед providers =
   parse-ошибка «expected llm_providers, COMMA, or RBRACE», поймано пробой).
   Обоснование значения: верхний общий знаменатель output-лимитов подключённых
   моделей (deepseek-chat ≤8k, groq Llama ≤8k, kimi/zai/cerebras/sakana ≥8k);
   8192 ток. ≈ 20–25 тыс. символов русского — покрывает самый длинный протокол
   (ОСП Deep, Эксперт: 4 слоя + 7 категорий + боевые вопросы, ЛЗ Deep Scan) с
   запасом. Понижение/повышение — через `METALOGOS_LLM_MAX_TOKENS` без правки
   репо (после деплоя владелец может подстроить).
2. Пометка обрезки на общем пути: `dept/miniapp.mlog` `pattern SendReport` —
   `llm_last_finish_reason()` == `length`/`max_tokens` → суффикс
   «⚠ ОТВЕТ ОБРЕЗАН ПО ЛИМИТУ max_tokens…» к любому отчёту отдела (апстрим
   доставляет усечённый текст — «the caller decides»; caller здесь добавляет
   честную пометку, вердикт «молчаливого успеха» больше невозможен).
3. **Фолбэк-совместимость (главное решение перехода).** Фичу #757 понимает
   ТОЛЬКО 0.27.1: пробы показали, что `max_tokens` в `llm{}` и билтин
   `llm_last_finish_reason()` дают parse-ошибку на 0.20/0.25/0.27.0
   («expected llm_providers, COMMA, or RBRACE» / «undefined: function»).
   Аварийный фолбэк entrypoint служит 0.20 тем же serve-файлом — без патча
   бут-фолбэк стал бы невозможен. Принято: при выборе фолбэка entrypoint
   вырезает фичу из serve-копии двумя sed-операциями
   (`/max_tokens: 8192,/d`; `s/llm_last_finish_reason()/""/g` — пометка
   выключается честно, не тишина). Граница — до вывода 0.20 из ротации
   (ADR-0009 «намеренно не включено»; FO-050/#182 ждёт апстрим-фикс VM).
4. Сопутствующее: CI-гвард №312 (.github/workflows/ci.yml) переведён с
   выведенного `bin/mlog-025` на `bin/mlog-027` (аудит dept-файлов фичи #757
   не несёт — паритет подтверждён B.2.3 ниже); `VENDORED_BINARIES`
   (tests/test_binary_exec_bit.py), `test_binary_prev_good_vendored`
   (tests/test_schedules_native.py), пары дуально-бинарных проб
   (test_n384_yana_delegation, test_fo376_osp_auth) — на mlog-027.

## Что проверено (методология ADR-0005…0009, блоки B.2–B.4)

1. **Статика `check app.mlog`:** rc=1 (известный базлайн долга №327),
   вывод **байт-идентичен** 0.27.0↔0.27.1 на файле БЕЗ фичи; на файле С фичей —
   0 parse error только на 0.27.1 (0.27.0/0.25/0.20 дают parse — учтено фолбэк-патчем).
2. **Статика `audit`** raw и с мостом №421: байт-идентичны 0.27.0↔0.27.1;
   гейт entrypoint: rc=2 (легально: «0 или 2»), «32 warnings, 304 passed»-профиль сохранён.
3. **Гвард dept-модулей:** 27/27 — rc байт-идентичны; 25 файлов — выводы
   байт-идентичны; `dept/design.mlog` и `dept/legal.mlog` — ТОЛЬКО новые
   warn-only диагностики [n486 types] (declared-return conflict — намеренное
   усиление 0.27.1, «the language stays dynamically typed»); новых [ERROR] нет.
4. **Байткод:** `compile` аугментированной копии rc=0 на обоих; .mbc
   1 910 214 (0.27.1) vs 1 910 193 байт (0.27.0). **Перекрёстное исполнение
   app-.mbc:** оба бинаря одинаково отказывают («deserialize: LimitExceeded» —
   байткод 1.9 МБ над лимитом дезериализатора; 0.27.0 отказывает и на СВОЁМ
   .mbc — поведение инвариантно версий, регресса нет). Поведенческий пробник —
   FO-056-фикстура `test_memory_fo056.mlog` (16 меток): **16/16 PASS на обоих**.
5. **Serve-батарея (B.3/B.4, ключевой минимум в среде исполнения):** полный
   старт `mlog serve` на аугментированной копии с env-allowlist ценза
   (entrypoint-путь): /health → `ok` на обоих; /version → `Unauthorized`
   (SEC-гейт честный) на обоих; scheduler/CSRF-cleanup/KV-SQLite стартуют
   идентично (визуально по логам старта).
6. **Фолбэк-патч:** sed-операции на аугментированной копии → `mlog-020 check`
   — 0 parse error, rc=1 (базлайн) — фолбэк-ветка бутстрапа остаётся живой.

## Что намеренно НЕ включено

- Выведение mlog-020 из ротации (ADR-0009): soak VM-пилота не пройден
  (FO-050/#182); фолбэк сохраняется, его совместимость обеспечена фолбэк-патчем.
- Догоняющая синхронизация dogfood_staging.mlog с фичей #757: производный
  артефакт стейджинга на 0.20-бинаре (mlog-020 check в CI) — фича несовместима
  по определению; синхронизация состоится при переходе стейджинга на новый
  бинарь (отдельный наряд).
- Пер-вызовный override (`call_llm(prompt, input, {max_tokens})`) — апстрим
  документировал как non-goal; блок-лимит + env покрывают офисный случай.
- Подбор значения 8192 «по живому длинному отчёту» — требуются прод-прогоны
  ОСП Deep/Эксперта с реальными ключами (Smoke-test #399, пункт приёмки
  владельцем после деплоя).

## Ожидаемые последствия

- Отчёты отделов больше не режутся на 1024 токенах: потолок 8192 + честная
  пометка при любом превышении.
- Обрезка наблюдаема в трёх местах: stderr-warning апстрима, JSONL-trace
  (`finish_reason`), суффикс в сообщении владельцу.
