## 1. Суть класса

Сообщения «ОСП/Яна: не удалось получить ответ» и тишина («Яна не отвечает») —
это гварды маршрута (app.mlog, ветки dept==osp / dept==yana / default): отдел
бросил исключение или вернул пустой ответ. Исключение НЕ падает наружу —
маршрут честно отказывает. До #771 E бросок ронял весь webhook (500, тишина).

## 3. Как читать отказ СЕЙЧАС (после G)

Сообщение отказа содержит строку «Причина: …» — это текст исключения
(redact "all", до 160 симв. на попытку, формат «первая || retry: вторая»).
Та же причина пишется в audit_log (действия `osp_empty_reply`,
`yana_empty_reply`, `yana_dispatch_fail`).

### Словарь причин и действий

| Причина | Значение | Что делать |
|---|---|---|
| `database is locked` | транзиентный write-лок (деплой/ночной слот/бэкап) | самоизлечимо: ретрай F покрывает ≈13 с; если повторяется чаще — смотреть, кто держит лок (ночные слоты, VACUUM) |
| `parse_json() error: EOF` | пустой ответ LLM-цепи (провайдер недоступен/ключ умер) | проверить ключи провайдеров (ZAI_API_KEY/DEEPSEEK_API_KEY), баланс, статус Z.ai |
| `HTTP_STATUS 401/403` | ключ отклонён / модуль вне allowlist | ротация ключа; для call_python — entrypoint allowlist |
| `ENV_NOT_FOUND` | голый `env()` без фолбэка | обернуть в env_or с дефолтом (класс №259) |
| пустой ответ (без «Причина:») | модель вернула пустоту / strip съел ответ | см. #771 D — пустой strip не применяется; проверить форму ответа модели |
| `HTTP_CONNECT … 127.0.0.1:4000` | llm_proxy не поднят | Render-лог прокси; бут-порядок entrypoint |

## 4. Правила поддержки (обязательные)

1. Любой НОВЫЙ dept-поток в маршруте — только через ретрай-хелперы
   (HandleYanaRetry / HandleOSPRetry / DispatchYanaDelegationRetry или свой
   аналог с захватом .error.message). Голый `TryVal(try Handle…)` в маршруте —
   красный флаг (тесты test_f/test_g краснят).
2. Любое новое «не удалось» обязано нести причину (G-паттерн THROW|).
3. Инвентарь n717 (`docs/office/interproc_inventory.md §1`) регенерировать при
   добавлении паттернов — гвард test_c2 краснит иначе.
4. Не читать `.value`/`.error` без обёртки: `try X` даёт Struct{ok, value,
   error} (ADR-0142); значение — TryVal(tr), причина — TryVal(try
   to_string(tr.error.message)) (идиом admin.mlog:491).

## 5. Что осталось открытым

- Маркеры в прод-БД недоступны агенту разработки (нет prod-токенов) — причина
  в сообщении владельца (G) закрывает разрыв: владелец пересылает отказ, в нём
  уже причина.
- Если «Причина: database is locked» повторяется ВНЕ окон деплоя — искать
  нового длинного писателя (слоты, бэкап) и чинить его, а не ретрай.

## 6. Корень трёх инцидентов (23-24.11) — гейт serve-чтений vs DATA_DIR (#771 H, PR #776)

**Симптом:** «Причина: [SANDBOX_VIOLATION] file I/O sandbox: resolved path
escapes sandbox: 'skills/…/SKILL.md'» — на каждом запросе, оба отдела.

**Механика:** гейт serve-чтений (№455) резолвит пути от CWD и ограничивает их
`METALOGOS_DATA_DIR`. Дефолт entrypoint `.` = корень приложения (ADR-0009),
но внешний env Render перебивал его — корпус (skills/, library/, config/)
оказывался вне сандбокса. `/health` exempt (health читает VERSION успешно) —
поэтому `/health` выглядел зелёным при мёртвых запросах. Апгрейд движка
~22-23.11 включил гейт — с этого момента и начались инциденты.

**Фикс:** (1) entrypoint форсирует `METALOGOS_DATA_DIR=$(pwd)` — абсолютный
корень приложения, громкий бут-лог «№771H … внешний env был: …» — по этой
строке в логе видно, какой env приходил извне; (2) `SkillFileRead` (dept/
skills.mlog) — try-грейс чтений корпуса, «громкий пропуск» (#623 W0): бросок
→ `''` → ответ уходит без скилла. 54 сайта по всем dept обёрнуты; гвард
test_h_no_ungated_corpus_reads_in_dept краснит любой новый голый read_file
в dept/*.mlog.

**Проверено:** проба n771h V3 (чужой DATA_DIR + фикс) — ответ уходит; V4
(DATA_DIR=app-root) — маркеры skills_index_missing/skills_undeployed
отсутствуют = скиллы реально грузятся в контекст.

**Правило:** новые чтения корпуса в dept-флоу — ТОЛЬКО через SkillFileRead.
Чтение движка `read_file` внутри serve-маршрута жёстко ограничено
DATA_DIR — пути вне корня приложения в проде запрещены конструкцией.

**Осторожно:** БД НЕ подчинена DATA_DIR (`db { url: env(DATABASE_URL) }`) —
перенос/смена DATA_DIR не трогает данные. kv-кэш (`data/metalogos_kv.db` —
профили-фолбэки, voice-настройки) — пересобирается сам.
