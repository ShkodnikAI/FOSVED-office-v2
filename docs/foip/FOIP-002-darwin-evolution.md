# FOIP-002: Самоэволюция проектов (Darwin Mode)

Статус: assessed
Дата: 2026-08-25
Источник: MetaHarness — Darwin Mode (npm run evolve), Weight-EFT

## Фаза 1: Излучение

**Суть:** MetaHarness умеет мутировать собственный конфиг: менять промпты, параметры, настройки, тестировать изменения в песочнице и оставлять только то, что измеримо улучшает результат. Модель заморожена — эволюционирует харнес.

**Проблема:** Наши проектные шаблоны будут иметь статические промпты. После 10 проектов мы поймём, что какой-то промпт фазы «design» даёт плохие результаты, но не будем это исправлять.

## Фаза 2: Оценка пригодности

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Решает реальную проблему? | **Отложено** — нужно сначала 5+ проектов для данных |
| 2 | Нативно на Металогос? | **Да** — SQL query на project_learnings + обновление template JSON |
| 3 | Нехватки Металогоса? | Нет |
| 4 | Усиливает существующие? | **Да** — улучшает качество будущих проектов |
| 5 | Совместимо? | **Да** — зависит от FOIP-001 (таблица project_learnings) |
| 6 | Нагрузка? | **Нулевая** — cron раз в неделю, один SQL + один call_llm |
| 7 | Риск потери? | **Нет** — эволюция меняет только template JSON, не код |

**Вердикт: ОТЛОЖИТЬ** до накопления ≥5 завершённых проектов. Таблица project_learnings создаётся в FOIP-001-N2, но логика ProjectEvolve реализуется позже.

## Зачем заранее

Таблица `project_learnings` нужна уже сейчас — она будет заполняться автоматически при каждом завершении фазы (verifier score записывается). Когда накопится достаточно данных — реализуем ProjectEvolve.

# FOIP-003: Умный роутинг моделей

Статус: assessed
Дата: 2026-08-25
Источник: MetaHarness — @metaharness/router

## Фаза 1: Излучение

**Суть:** MetaHarness router выбирает самый дешёвый LLM провайдер, который справится с задачей, на основе исторических логов. Обучается на собственных результатах. У нас сейчас parallel provider racing — 3-5 провайдеров гоняются одновременно, самый быстрый выигрывает. Дорого и ненадёжно.

## Фаза 2: Оценка пригодности

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Решает реальную проблему? | **Да** — экономия токенов на Render free tier |
| 2 | Нативно на Металогос? | **Частично** — SQL query работает, но нужна агрегация |
| 3 | Нехватки Металогоса? | Нет (SQL хватит для простой эвристики) |
| 4 | Усиливает существующие? | **Да** — заменяет parallel racing |
| 5 | Совместимо? | **Да** — но требует изменения llm_proxy.py |
| 6 | Нагрузка? | **Снижает** — один вызов вместо 3-5 параллельных |
| 7 | Риск потери? | **Средний** — если роутер выберет слабую модель, качество упадёт |

**Вердикт: ОТЛОЖИТЬ** — после FOIP-001. Причина: роутинг зависит отdept-специфичных метрик качества, а сейчас нет единой системы оценки. Нужен llm_verifier integration во все отделы (сейчас только в dev, design, expert, osp, qa).

# FOIP-004: Итеративная разработка с rollback (AVO)

Статус: assessed
Дата: 2026-08-25
Источник: MetaHarness — Governed Autonomous Variation

## Фаза 1: Излучение

**Суть:** MetaHarness AVO позволяет агенту итеративно улучшать результат: проверить → изменить → выполнить → оценить → откатить если хуже. С детерминистическим proof на 205 действий. У нас сейчас: одна попытка call_llm, если результат плохой — фаза помечается failed.

## Фаза 2: Оценка пригодности

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Решает реальную проблему? | **Да** — LLM часто даёт mediocre результат с первого раза |
| 2 | Нативно на Металогос? | **Да** — while loop + call_llm + llm_verifier |
| 3 | Нехватки Металогоса? | Нет |
| 4 | Усиливает существующие? | **Да** — встроить в ProjectRunPhase |
| 5 | Совместимо? | **Да** — часть orchestrator'а (FOIP-001-N3) |
| 6 | Нагрузка? | **Умеренно** — до 3x больше LLM вызовов на фазу |
| 7 | Риск потери? | **Нет** — добавляется поверх, не заменяет |

**Вердикт: ПРИНЯТЬ** — реализовать как часть FOIP-001-N3 (ProjectRunPhase).

## Фаза 3: Сравнение

| Аспект | Сейчас | Будет | Преимущество |
|--------|--------|-------|--------------|
| Генерация кода | 1 попытка call_llm | До 3 попыток с verifier | Качество кода выше |
| Ошибка в фазе | «Фаза завершилась с ошибкой» + ручной повтор | Автоматический повтор с контекстом ошибки | Меньше ручного вмешательства |
| Расход токенов | 1x | До 3x (в худшем случае) | Точечно: повтор только при score < 0.7 |

# FOIP-005: Анализ GitHub-репо перед проектом

Статус: assessed
Дата: 2026-08-25
Источник: MetaHarness — `analyze-repo` + `score`

## Фаза 1: Излучение

**Суть:** MetaHarness может прочитать любой GitHub репозиторий (без выполнения кода) и recommend: какие агенты нужны, какой стек, оценка стоимости. У нас пользователь даёт ссылку на репо, но мы её не анализируем — просто передаём как URL для push.

## Фаза 2: Оценка пригодности

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Решает реальную проблему? | **Да** — контекст существующего репо улучшает генерацию |
| 2 | Нативно на Металогос? | **Частично** — GitHub API через http_get, но нужен **LR-001** (base64 для README) |
| 3 | Нехватки Металогоса? | LR-001 (base64_encode) — workaround: читать через raw.githubusercontent.com |
| 4 | Усиливает существующие? | **Да** — Dev получает реальный контекст проекта |
| 5 | Совместимо? | **Да** — часть orchestrator'а |
| 6 | Нагрузка? | **Минимальна** — 2-3 HTTP запроса к GitHub API |
| 7 | Риск потери? | **Нет** |

**Вердикт: ПРИНЯТЬ** — реализовать как `ProjectAnalyzeRepo` в orchestrator'е. Workaround для base64: читать файлы через raw.githubusercontent.com (plaintext), не через Contents API (base64).

## Фаза 3: Сравнение

| Аспект | Сейчас | Будет | Преимущество |
|--------|--------|-------|--------------|
| GitHub контекст | URL передаётся как строка | Файловая структура, стек, зависимости определяются автоматически | Генерация кода учитывает реальный проект |
| Определение стека | Нет | Парсинг package.json/requirements.txt/Cargo.toml | Dev получает правильный контекст |

# FOIP-006: Figma-интеграция (двунаправленная)

Статус: rejected
Дата: 2026-08-25
Источник: Figwright (awdr74100/figwright)

## Фаза 1: Излучение

**Суть:** Figwright — MCP-сервер + Figma-плагин, позволяющий AI-агенту читать и писать на Figma канвасе. 112 инструментов. Бесплатно, без Dev Mode.

## Фаза 2: Оценка пригодности

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Решает реальную проблему? | **Слабо** — нет активного использования Figma в workflows |
| 2 | Нативно на Металогос? | **Нет** — нужен MCP-сервер (Node.js) + Figma-плагин |
| 3 | Нехватки Металогоса? | MCP-протокол не поддерживается |
| 4 | Усиливает существующие? | Нет — новая независимая система |
| 5 | Совместимо? | **Сложно** — отдельный Node.js процесс + WebSocket + Figma desktop |
| 6 | Нагрузка? | **Высокая** — Node.js MCP server + Figma plugin = RAM |
| 7 | Риск потери? | Нет |

**Вердикт: ОТКЛОНИТЬ** — не подходит текущей архитектуре (Telegram-first офис, Render free tier). Требует отдельного MCP-инфраструктуры и Figma desktop app. Возможно пересмотреть при переходе на платный tier или при появлении MCP-поддержки в Металогосе.

**Сохранённые идеи на будущее:**
- Provider-first подход (определять стек целевого проекта)
- Design diff (инкрементальные обновления по дизайну)
- Component grounding (переиспользование существующих компонентов)
