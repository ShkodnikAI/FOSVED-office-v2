# Гигиена репозитория (FO-012)

Наряд: [FO-012, issue #72](https://github.com/ShkodnikAI/FOSVED-office-v2/issues/72).
Дата внедрения: 2026-09-12.

## Проблема

На аудите 2026-09-12 репо весило 193 МБ: `skills/` = 62 МБ (копия 248 каталогов
скиллов), `bin/` = 71 МБ (три бинарника, включая устаревшие `*_bak`), плюс 50
веток вне `main` (аудит docs/branches-audit.md от 2026-08-09). Каждый клон и
каждый CI-прогон платили за всё это.

## Что сделано

### 1. `skills/` выведен из git → релиз-артефакт

Скиллы читаются рантаймом (`app.mlog`, `dept/*.mlog` — `read_file("skills/<имя>/SKILL.md")`,
в том числе по динамическому имени из индекса), поэтому просто удалить их из
репо нельзя — офис на деплое останется без скилл-контекста. Принятое решение:

- **Каноничный снапшот** — GitHub Release этого же репозитория:
  тег `skills-snapshot-2026-09-12`, ассет `skills-snapshot-2026-09-12.tar.gz`
  (sha256 `afb74161ec6ba2a9322e67f8ad24d555ebec84c01a1d063cc6bddb85e7ae5e2b`).
- **Манифест** `skills-manifest.json` (в git): тег снапшота, sha256 архива,
  список всех 248 скиллов с хешами SKILL.md. Изменение скиллов = новый снапшот
  + новый коммит манифеста — источник и хеш всегда зафиксированы.
- **Bootstrap при деплое**: `entrypoint.sh` вызывает `scripts/bootstrap_skills.sh`,
  который разворачивает `skills/` из релиза (с проверкой sha256), если их ещё нет.
  Токен берётся из env: `GITHUB_TOKEN_SKILLS` → `GITHUB_TOKEN_METALOGOS` →
  `GITHUB_TOKEN` → `GH_TOKEN`. Рекомендуется завести `GITHUB_TOKEN_SKILLS`
  (read-доступ к репо) в env сервиса Render.
- **Деградация не фатальна**: если токена нет или релиз недоступен, офис
  стартует, но скилл-контекст департаментов будет пуст (WARNING в логе).
- **Обновление снапшота**: `python3 scripts/skills_snapshot.py` → архив и новый
  манифест; создать Release, залить ассет, закоммитить манифест.

### 2. `bin/` — стратегия «один бинарник + версия в имени коммита»

Старые бинарники `mlog_old_*` были удалены из HEAD раньше (история не
переписывается — наряд считает это опциональным). В `bin/` остаётся ровно один
`mlog`; версия фиксируется коммитом и проверяется CI-job «Version consistency»
(VERSION ↔ README ↔ `mlog --version`). Полный клон по-прежнему несёт старые
бинарники в истории — их вымывание потребовало бы rewrite истории, что
сознательно не делается (риск > выгоды; CI качает shallow-клон и мусора не видит).

### 3. Ветки — политика и разовая чистка

Политика (дополнение к docs/branches-audit.md):

- Ветка живёт **≤ 30 дней** с момента последнего коммита, если не влитая.
- Влитая ветка **удаляется сразу после мержа** PR.
- Раз в месяц — сверка `git branch -r --merged origin/main`: всё смерженное
  старше 7 дней удаляется.

Разовая чистка 2026-09-12: удалены все 8 веток вне `main`
(`fo-001…fo-007`, `fix/vm-serve-compat`) — все полностью влиты в `main`.
После чистки: **0 веток вне main**.

### 4. `.gitignore`

Добавлено: `skills/`, `artifacts/`, `*.tar.gz`, `*.sql.gz`, `dumps/`, `*.dump`.

## Итог

| Метрика | До | После |
|---|---|---|
| Checkout HEAD | ~95 МБ | ~33 МБ |
| Скачивание CI (shallow) | ~95+ МБ | ~30 МБ |
| Ветки вне main | 8 (исторически 50) | 0 |
| Скиллы в git | 62 МБ / 1108 файлов | манифест 12 КБ |

Полный (не shallow) клон всё ещё содержит историю со старыми бинарниками и
скиллами (~100 МБ `.git`). Сокращение истории — опциональный отдельный шаг
(rewrite сломает SHA всех коммитов после точек слияния); по наряду он не
обязателен и не выполнялся.
