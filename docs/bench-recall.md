# Наряд №852 — бенчмарк recall на golden-наборе офиса: LIKE vs морфология vs sqlite-vec

**Мета:** волна 73 (W-M), P2, класс [office]emory][benchmark]. Диспатч волны: Metalogos gh#1677. Наряд: gh#1676.
**Харнесс:** `scripts/bench_recall.py`. **Golden-набор:** `tests/golden/recall_golden.json` (62 запроса).
**Дата замера:** 2026-10-31. Среда замера: python 3.12, sqlite-vec 0.1.9, model2vec 0.10.0 (статические эмбеддинги `minishlab/potion-multilingual-128M`, 256 dim), всё локально — данные офиса не покидают контур, внешние API не используются (граница наряда).

## Методика

- **Корпус** — реальные офисные артефакты репо (не синтетика): `docs/*.md`, `docs/adr/*.md`, `docs/departments/*.md`, `docs/projects/**/*.md`, отчёты нарядов в корне (`report_*.md`), `library/*.md`. Экстракция детерминированная: одна строка = одна запись, чистка markdown, дедупликация, эвристика 13 типов FosvedMemory, явный fail-closed source `doc:<путь>` (№849). Итог: **4666 записей**.
- **Посев** — через прод-поверхность `FosvedMemory.remember()` (не мимо неё). Конфликт-детектор при севе: **0 superseded** — целостность разметки не нарушена, все релевантные записи остались видимыми.
- **Golden-набор** — 62 запроса трёх видов, сформулированных как реальные брифинговые запросы к памяти офиса: keyword (26), question (20), paraphrase (16). Каждый запрос размечен на релевантную запись через `{file, needle}` — уникальная подстрока строки артефакта; разрешение детерминированное и проверяемое тестом. Разметка «найдено/пропущено» считается харнессом **по фактической выдаче**, не по памяти составителя.
- **Метрики:** hit@5 (релевантная запись в топ-5), MRR@5, доля пустых выдач.
- **Порог решения из наряда:** апгрейд поиска, если LIKE hit@5 < 0.7.

## Контур видимости (паритет №849/№850/№851)

Все контуры работают на одинаковой поверхности видимости: `confidence >= 0.3`, не superseded, не purged (№850), не declined (FO-020). Контур (а) — это сама прод-поверхность `recall()`; контуры (б)/(в) повторяют фильтр видимости SQL-запросом-зеркалом и отличаются только способом сопоставления запроса с содержимым.

## Метрики (62 запроса)

| Контур | hit@5 | MRR@5 | пустых |
|---|---|---|---|
| (а) **like** — прод-поверхность (SQL `LIKE '%запрос%'`) | **0.000** | **0.000** | **100%** |
| diag: like одиночным токеном (лучший случай LIKE) | 0.210 | 0.108 | 27.4% |
| (б) **morph** — LIKE + морфологическая нормализация (RU/EN стеммер) | **0.484** | 0.392 | 0% |
| (в) **vec** — sqlite-vec + potion-multilingual-128M (локально, без API) | **0.452** | 0.317 | 0% |

По видам запросов:

| Вид запросов | like | diag (1 токен) | morph | vec |
|---|---|---|---|---|
| keyword (n=26) | 0.000 | 0.308 | **0.654** | 0.615 |
| question (n=20) | 0.000 | 0.150 | **0.400** | 0.200 |
| paraphrase (n=16) | 0.000 | 0.125 | 0.312 | **0.500** |

## Что показал замер

1. **Прод-поверхность LIKE на реалистичных запросах — 0.000 hit@5, 100% пустых выдач.** Причина механическая и проверяемая: SQL-фильтр `fosved_memory.py` — **whole-phrase подстрока** (`lower(content) LIKE '%<весь запрос>%'`). Любой многословный запрос проходит только как дословная фраза записи. Прод так не ломается только потому, что штатные вызовы recall — короткие однословные метки (`"LZ Daily"`), а `/memory/recall` с развёрнутой фразой сегодня заведомо возвращает пусто.
2. **Потолок LIKE (диагностика лучшего случая, одиночный токен): hit@5 = 0.210.** Даже в наиболее благоприятном для LIKE режиме (одно слово, морфология запрашивающего угадана) прод-поверхность покрывает меньше четверти golden-набора; 27% запросов остаются пустыми из-за словоформ.
3. **Морфологическая нормализация (дешёвый апгрейд): hit@5 = 0.484, MRR@5 = 0.392.** Лёгкий детерминированный RU/EN стеммер без зависимостей поднимает покрытие с 0.210 до 0.484 (×2.3), пустые выдачи исчезают полностью.
4. **Локальные эмбеддинги (sqlite-vec): hit@5 = 0.452, MRR@5 = 0.317.** На парафразах — лучший результат (0.500 против 0.312 у морфологии: синонимия и перефразирование без общих корней), на вопросах — слабее морфологии (0.200: вопросительные конструкции размывают вектор статической модели).

## Решение — числами

- Порог наряда: апгрейд, если LIKE hit@5 < 0.7. **Факт: 0.000 (прод), 0.210 (потолок) — порог превышен на любой интерпретации → АПГРЕЙД ОБОСНОВАН.**
- **Ступень 1 (дешёвая, немедленно): морфологическая нормализация** сопоставления в recall-пути — 0.210 → 0.484 hit@5 без новых зависимостей, без выкачивания моделей, тем же ранжированием (semantic × decay × confidence × review).
- **Ступень 2 (поверх №851-поверхности): эмбеддинг-контур** — закрывает парафразы (0.312 → 0.500 против морфологии), требует sqlite-vec + локальной статической модели (~30 МБ, без API).
- Вопросы у чистого vec-контура слабее морфологии (0.200 против 0.400) — **гибрид morph+vec** (морфология как база, эмбеддинги как добор на пустых/парафразных запросах) — основная гипотеза внедрения, проверяется на золотом наборе тем же харнессом.
- **Внедрение любого контура — отдельный наряд** (граница №852): здесь только измерение, прод-код `lib/fosved_memory.py` не тронут.

## memanto в shadow

Харнесс несёт режим `--shadow-cmd '<команда>'`: команда получает запрос на stdin, печатает JSON-выдачу; совпадение с golden-разметкой — по содержимому записей; записи в прод не идут (shadow-first, урок №581/№840). Локальный режим memanto (Docker + Ollama) физически размещается на сервере офиса — в среде замера Docker/Ollama недоступны, shadow-прогон не подделывался. Заявленные авторами метрики (89.8% LongMemEval / 87.1% LoCoMo) — внешний эталон **на других наборах** и с нашим golden не сливались.

## Ограничения (честно)

- Golden-набор собран из реальных артефактов **репо**; прод-журналы брифингов/прокси живут на сервере офиса (`data/` вне git). При переносе замера на сервер набор расширяется реальными запросами из журналов через тот же харнесс — разметка «по выдаче» и механика метрик не меняются. Вывод по порогу на текущем наборе устойчив (разрыв 0.000/0.210 против порога 0.7 — четырёхкратный, вид набора запросов не меняет вердикт).
- Эвристика типов корпуса (`_memory_type`) и границы длины строки — свойства экстракции, не прод-данных; влияют на состав корпуса одинаково для всех контуров.
- Эмбеддинг-модель — статическая (model2vec/potion-multilingual-128M). Полные трансформер-эмбеддинги могут дать выше; сравнение — в наряде внедрения.
