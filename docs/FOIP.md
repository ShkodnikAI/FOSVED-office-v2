# FOIP — FOSVED Office Improvement Protocol

> Версия 1.0 · Обязательный протокол для любого изменения офиса
> 
> **Принцип:** Офис только улучшается. Накопленные способности не теряются.
> Удаляется только то, что идёт под замену или откровенный мусор.

---

## 0. Зачем этот протокол

Без протокола каждое изменение несёт риски:
- **Накопление мусора** — новый функционал добавляется рядом со старым, старый не удаляется
- **Потеря способностей** — чистка «лишнего» случайно убивает рабочее
- **Несовместимость** — новая фича ломает существующую логику
- **Расползание scope** — маленькое улучшение вырастает в незаконченный монстр

FOIP обязывает пройти 8 фаз **до написания кода**. Каждая фаза производит артефакт. Пропуск фазы = нарушение протокола.

---

## 1. Фазы протокола

### Фаза 1: Излучение (Discovery)

**Цель:** Найти идею, фичу, подход, который может улучшить офис.

**Источники излучения:**
- Исследование Open Source репозиториев (MetaHarness, Figwright, и т.д.)
- Анализ логов ошибок и user feedback
- Сравнение с конкурентами
- Идеи от владельца
- Самоанализ офиса (слабые места, отсутствующие возможности)

**Артефакт:** Краткое описание идеи (2-5 предложений) + ссылка на источник.

**Формат:**
```
[DISCOVERY] <название>
Источник: <ссылка или «внутренняя»>
Суть: <что это и какую проблему решает>
```

---

### Фаза 2: Оценка пригодности (Assessment)

**Цель:** Определить, подходит ли идея нашей архитектуре и Металогосу.

**Чеклист (все пункты обязаны к ответу):**

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Решает ли это реальную проблему офиса? | |
| 2 | Можно ли реализовать нативно на Металогос? | Да / Частично / Нет |
| 3 | Если частично/нет — какие функции Металогоса не хватает? | Список |
| 4 | Усиливает ли это существующие отделы или требует новый? | |
| 5 | Совместимо ли с текущей архитектурой (mlogserver, call_llm, DB, llm_proxy)? | |
| 6 | Насколько это нагружает Render free tier (512MB RAM, 0.1 vCPU)? | |
| 7 | Есть ли риск потери существующих способностей? | |

**Артефакт:** Заполненная таблица + вердикт: **ПРИНЯТЬ** / **ОТЛОЖИТЬ** / **ОТКЛОНИТЬ**.

Если ОТЛОЖИТЬ — указать что нужно для принятия (например, «ждём base64_encode в Металогос»).
Если ОТКЛОНИТЬ — обоснование (сохраняется для истории — возможно, ситуация изменится).

---

### Фаза 3: Сравнительный анализ (Comparison)

**Цель:** Чётко показать, что меняется. Что удаляется, что добавляется, что улучшается.

**Обязательная таблица:**

| Аспект | Сейчас | Будет | Преимущество |
|--------|--------|-------|--------------|
| (компонент 1) | (как работает) | (как будет работать) | (что улучшается) |
| (компонент 2) | ... | ... | ... |

**Обязательный раздел: Что удаляется**
```
УДАЛЯЕТСЯ:
- <файл/функция/таблица> — причина: заменяется на <новое>
- <файл/функция> — причина: неработающий/мёртвый код

НЕ УДАЛЯЕТСЯ (сохраняется):
- <файл/функция> — причина: используется в <контекст>
```

**Обязательный раздел: Что добавляется**
```
ДОБАВЛЯЕТСЯ:
- <файл/функция/таблица> — назначение

ПЕРЕРАБАТЫВАЕТСЯ (замена старого на новое):
- <старое> → <новое> — что улучшается
```

**Обязательный раздел: Проверка сохранения способностей**
```
СПОСОБНОСТЬ: <название>
Была реализована в: <старое место>
После изменения: <новое место или «сохраняется»>
Риск потери: Нет / Низкий / Средний
Как проверяем: <тест-сценарий>
```

---

### Фаза 4: Архитектурное решение (Architecture)

**Цель:** Определить точное место в архитектуре.

**Чеклист:**
- [ ] Куда идёт код: новый файл / существующий файл (какой)
- [ ] Какие таблицы БД нужны (DDL)
- [ ] Какие изменения в InitDB
- [ ] Какие изменения в роутинге (app.mlog)
- [ ] Какие изменения в llm_proxy.py (если нужны)
- [ ] Какие изменения в entrypoint.sh (если нужны)
- [ ] Затрагивает ли другие отделы

**Артефакт:** Конкретный план изменений по файлам.

---

### Фаза 5: План внедрения (Plan)

**Цель:** Разбить на наряды (задачи) с чёткими границами.

**Формат наряда:**
```
НАРЯД: <ID>
Название: <краткое название>
Тип: feature / fix / refactor / cleanup / lang-request
Приоритет: P0 (критичный) / P1 / P2 / P3
Зависимости: <список ID нарядов>

Описание:
<что конкретно сделать>

Файлы:
- [ ] <файл> — <что изменить>

Тестирование:
- <сценарий 1>
- <сценарий 2>

Критерий готовности:
<как понять, что наряд выполнен>

Откат при провале:
<как вернуть к состоянию до изменения>
```

**Тип `lang-request`** — если Металогосу не хватает функции:
```
НАРЯД LANG-REQUEST: <ID>
Необходимая функция: <название и сигнатура>
Пример использования: <код на Металогос>
Альтернатива пока нет функции: <workaround>
Критичность: блокер / можно обойти
```

---

### Фаза 6: Внедрение (Execution)

**Правила:**
1. Нарыды выполняются **строго по порядку зависимостей**
2. Каждый наряд — отдельный коммит с ID наряда в сообщении
3. Между нарядами — **обязательный тест** (см. Фазу 7)
4. Если тест провалился — откат и анализ перед повтором
5. Нельзя начинать следующий наряд, пока предыдущий не прошёл тестирование

---

### Фаза 7: Верификация (Verification)

**Обязательные проверки после каждого наряда:**

1. **Парсинг:** `mlog check` не должен выдавать ошибок
2. **Деплой:** Офис поднимается, `/health` отвечает 200
3. **Регрессия:** Все команды из `/help` работают
4. **Специфичный тест:** Сценарий из наряда проходит
5. **Сохранение способностей:** Сценарии из Фазы 3 (Проверка сохранения) проходят

**Формат отчёта о тестировании:**
```
VERIFICATION: <ID наряда>
Дата: <YYYY-MM-DD>

[ ] mlog check — чисто
[ ] /health — 200
[ ] /help — полный список команд
[ ] <специфичный тест 1> — PASS/FAIL
[ ] <специфичный тест 2> — PASS/FAIL
[ ] <регрессия: способность X> — PASS/FAIL
[ ] <регрессия: способность Y> — PASS/FAIL

Итог: PASS / FAIL
Причина провала (если есть): <описание>
```

---

### Фаза 8: Обогащение языка (Language Enhancement)

**Цель:** Если в Фазе 2 обнаружилась нехватка функций Металогоса.

**Процесс:**
1. Наряд `lang-request` создаётся в Фазе 5
2. Реализуется workaround для текущего внедрения
3. `lang-request` передаётся разработчику Металогоса
4. Когда функция появляется — workaround заменяется на нативную реализацию
5. Старый workaround удаляется

**Принцип:** Напрягаем язык, а не обходим его костылями. Каждый workaround — временный.

## 2. Правила безопасности

### 2.1 Что НЕЛЬЗЯ удалять без протокола

- Любой `pattern` который вызывается хотя бы из одного места (проверить через `rg`)
- Любую таблицу БД с данными (сначала миграция данных, потом удаление)
- Любой маршрут (`route`) без замены на эквивалентный
- Любой навык отдела (skill) без проверки что替代覆盖 тот же функционал

### 2.2 Что МОЖНО удалять без полного протокола

- Файлы с `_deprecated_` префиксом (мёртвый код)
- Комментарии с `TODO` старше 30 дней, не связанные с активными задачами
- Дублированный код, если есть proof что он не вызывается (rg + тест деплоя)

### 2.3 Защита от деградации Яны

Яна — центральный интеллект офиса. Её деградация = крах офиса.

**Обязательное правило при любом изменении Яны:**
1. До изменения: прогоняем 5 тестовых запросов через Яну, записываем ответы
2. После изменения: прогоняем те же 5 запросов, сравниваем
3. Если любой ответ стал хуже — откат

**Запрещено:**
- Удалять gates (YanaGate*) без замены на эквивалентную защиту
- Упрощать anti_format блок без тестирования на известных проблемных запросах
- Менять делегационную логику без проверки всех отделов-получателей

## 3. Использование протокола

### Для каждого предложения улучшения:

1. Создаём файл `docs/foip/<ID>-<название>.md`
2. Проходим Фазы 1-5, записываем в файл
3. После реализации — добавляем результаты Фаз 6-7
4. Файл остаётся в репо как история решений

### Формат файла:
```markdown
# FOIP-<ID>: <Название>

Статус: discovery / assessed / planned / in-progress / verified / rejected
Дата: <YYYY-MM-DD>
Автор: <кто предложил>

## Фаза 1: Излучение
...
## Фаза 2: Оценка
...
## Фаза 3: Сравнение
...
## Фаза 4: Архитектура
...
## Фаза 5: Нарыды
...
## Фаза 6-7: Результат внедрения
...(заполняется после реализации)
```
