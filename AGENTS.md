# AGENTS.md — методология работы с FOSVED-office-v2

> Не замена README/REFERENCE-документации проекта. Это точка входа в
> **методологию**: где лежит правда по каждому классу вопроса, каких
> ошибок избегать, что значит «наряд сделан». Прочитать первым, до
> любой задачи.
>
> Адаптировано из `AGENTS.md` проекта Metalogos (тот же класс дисциплины,
> проверенный на практике в более зрелом и более крупном проекте) —
> не скопировано вслепую, каждый пункт переведён на реальные инциденты
> именно этого репозитория.

---

## 1. Главное правило: код — источник правды, не проза

Комментарии, README, наши же прошлые отчёты **могут разойтись с
реальным кодом** — не потому что кто-то соврал, а потому что код
меняется быстрее, чем описание рядом с ним. За одну эту сессию редизайна
было минимум три случая: README описывал систему до FO-008 (монолитный
`llm_proxy.py` на 5456 строк, Metalogos v0.12.0, 22 таблицы) — реальность
разошлась по всем пунктам. Наряд FORGE-UI-10 был написан с предположением
«Telegram/YouTube/TikTok не реализованы» — реальность оказалась
обратной, MON-1…4 уже закрыты. `DEPT_COLORS` был сведён к одному
акценту по ошибочному выводу «раз SPA не красит навигацию, значит и
здесь не нужно» — без проверки исходного наряда.

**Правило:** прежде чем действовать по текстовому описанию чего-либо в
проекте — **проверь фактом**: `grep` по реальному коду, реальный запуск,
реальный лог. Не «README говорит X» → «действую из X», а «README говорит
X» → «grep подтверждает X» → «действую».

## 2. Идентичность офиса — не копировать общие решения бездумно

FOSVED-office-v2 — не универсальный чат-бот с départements-обвязкой.
Метафора «Диспетчерская» (или её преемник — новый тёмно-красный язык)
задаёт не только цвет, а принцип: каждый отдел — самостоятельный
специалист со своим голосом, не прокси к одной большой модели. При
добавлении новой возможности — не «как это делают другие боты», а «как
это должно быть здесь, если делать честно и по принципам проекта».

**Практическое следствие:** если результат сводится к «просто вызвали
внешний API так же, как это сделал бы любой другой Python-скрипт» — это
обёртка, не часть системы. Признак настоящей интеграции — новая
возможность, использующая уже существующие механизмы (Guardian, `dept_activity`,
`DEPT_COLORS`, наряды), а не отдельный остров рядом с ними.

## 3. Граница решений — где действовать самостоятельно, где спрашивать

**Действовать самостоятельно, не спрашивая разрешения на каждый шаг:**
инженерно-эстетические решения — структура файла, сигнатура функции,
формулировка текста, выбор конкретной библиотеки для нового коннектора.
Здесь решает инженерный вкус, не стратегия продукта.

**Спрашивать явного решения владельца, не предполагать:**
необратимые действия (перезапись истории git, удаление данных),
и всё, что меняет идентичность проекта — пересмотр уже принятых решений
(например: разноцветные `DEPT_COLORS` по отделам — принято и подтверждено
в этой сессии дважды, не пересматривать без явного запроса; тёмная тема
с красным акцентом как основной язык — принято, замена логотипа), новая
смысловая сущность (не механическое расширение существующей — например,
«ещё один MCP-сервер с новым источником» это расширение, а «переход на
принципиально другую архитектуру подключения ИИ» — нет).

## 4. Синхронизация — самая частая собственная ошибка

**В этой сессии несколько раз** действия предпринимались по устаревшему
локальному чекауту, хотя `git checkout origin/main` вроде бы был вызван.
Причина — предыдущий `fetch` кэшировал состояние ДО того, как нужный
мерж произошёл, и последующий checkout закреплял именно устаревшее
состояние.

**Обязательная последовательность перед любой проверкой:**
```bash
git fetch origin main --force
git log origin/main -1 --format='%H %ci %s'   # посмотреть, что реально пришло
git checkout -q origin/main
git log -1 --format='%h %s'                    # подтвердить совпадение с предыдущей строкой
```
Если `git fetch` печатает `xxxxx..yyyyy main -> origin/main` — значит
ветка РЕАЛЬНО продвинулась только что, не была актуальна и раньше.

## 5. Где лежит правда — по классу вопроса

| Вопрос | НЕ смотреть (может устареть) | Смотреть (источник правды) |
|---|---|---|
| Существует ли команда `/dept ...`? | README, память о прошлой сессии | `grep 'starts_with(text, "/' app.mlog` |
| Работает ли реально фича X? | Закрытый issue/PR | Реальный запуск (`mlog run`, `curl`, Flask test_client) |
| Какой цвет у отдела Y? | Память, старые скриншоты | `DEPT_COLORS` в `proxy/core.py`, текущий `main` |
| Подключён ли MCP-источник Z? | Название файла/наряда | `guardian_base.json` — реально ли есть правило `allow`, и `METALOGOS_MCP_ALLOWLIST` в `render.yaml` |
| Сколько таблиц/команд/строк в проекте? | Число в прошлом отчёте | Пересчитать напрямую (`grep -c`, `wc -l`) — числа устаревают между сессиями |
| Что реально проверяет CI/деплой? | Название джобы | Сам workflow-файл — что он реально запускает |
| Актуальна ли ветка перед мержем? | «Недавно фетчил» | Вывод `git fetch` — есть ли `xxxxx..yyyyy`, не «показалось» |

## 6. Быстрый поиск прошлых решений — не перечитывать всю историю чата

Прошлые решения этого проекта разбросаны по коммитам, PR и переписке,
не в едином индексе (в отличие от Metalogos, где есть `docs/adr/`) —
**это первое, что стоит завести** (см. §9). До тех пор:
```bash
git log --all --grep="ключевое слово" --oneline
```
Частые темы, где решение уже принято — не переоткрывать без явного
запроса владельца:
- Разные цвета отделов (`DEPT_COLORS`) — не сводить к одному акценту.
- Тёмно-красная тема с логотипом FOSVED — основной язык интерфейса,
  «Диспетчерская» — предыдущая эпоха, не текущая.
- MCP-коннекторы — только через `search_mcp_registry`/явное согласие,
  Guardian deny-by-default.

## 7. Типичные собственные ошибки при работе с этим кодом

**Ложные выводы из grep по неверному месту.** `BASE_DIR` в `proxy/core.py`
была определена дважды в одном файле с разной логикой — вторая
(неверная) переопределяла первую при загрузке модуля. Простой `grep`
по одному вхождению этого не поймал бы — нужна проверка РЕАЛЬНОГО
значения переменной после загрузки (`python3 -c "from proxy.core import BASE_DIR; print(BASE_DIR)"`), не чтение исходника глазами.

**`exec()` в теле роута `mlog serve` заперт отдельным гейтом**
(`METALOGOS_SERVE_ALLOW_EXEC`), отличным от гейта верхнего уровня
(`METALOGOS_ALLOW_EXEC`). Функция, вызываемая изнутри route-блока
(как `AdminNightCycle` из `app.mlog:4833`), не может полагаться на
`exec()`, даже если он разрешён для `mlog run`/`check`.

**Формат вывода внешней библиотеки может измениться без предупреждения.**
`aliens-eye` (OSINT-сканер) сменил интерфейс командной строки и формат
JSON дважды с момента написания исходного наряда — код обращался к
несуществующему более интерфейсу. Единственный надёжный способ
проверить — реально установить и запустить библиотеку, не полагаться
на память обучения или на комментарии в коде.

**Reuters закрыл публичные RSS-ленты около 2020 года** (по памяти
обучения, не проверено вживую сетевым запросом из песочницы) — лента
`feeds.reuters.com` в `RSS_FEEDS` может годами молчать, не бросая
ошибку (`feedparser` на мёртвом URL просто отдаёт пустой список).

## 8. Контракт наряда — что значит «сделано»

1. Ветка → `git push` в удалённый репозиторий → **PR открыт**. Ветка,
   оставленная только локально или запушенная без PR, не считается
   сданной, независимо от готовности кода.
2. Каждая заявленная функция подтверждена **реальным** прогоном — не
   только чтением кода, а `mlog run`/`mlog check`, реальным HTTP-вызовом
   через `test_client` или настоящий сервер, визуальным рендером через
   Playwright для фронтенда. Не «должно работать», а «проверено,
   работает».
3. Если наряд подразумевает несколько отдельных изменений — один
   коммит на один логический шаг, не одна большая свалка, если это
   резко не увеличивает объём работы.
4. Отчёт называет явные допущения и то, что осталось нерешённым — не
   выдаёт частичный результат за полный. Если что-то помечено «нужен
   отдельный наряд» — это не признание поражения, это честность.
5. Перед началом работы над существующим нарядом — проверить, не
   реализовано ли уже то, что наряд просит (см. §4 про синхронизацию) —
   FORGE-UI-10 пришлось чинить именно по этой причине уже после подачи.

## 9. Что нужно завести, но пока не существует централизованно

- **Индекс решений (аналог `docs/adr/`).** Решения этой сессии —
  разноцветные отделы, тёмная тема, отказ от Ozon-парсинга сверх
  честного статуса «заблокирован» — зафиксированы в текстах коммитов,
  не в едином, по темам, индексе. Первый шаг приведения проекта в
  порядок — завести `docs/adr/` и ретроактивно описать 5-10 ключевых
  решений этой сессии, прежде чем добавлять новые.
- **Журнал типичных ошибок** (расширение §7 этого документа) — вести
  как живой список, не единоразовый.
- **CI-гейт «ветка не отстала от main»** — тот же наряд #161/#182 из
  Metalogos у нас тоже случался неявно (устаревшие локальные чекауты,
  описанные в §4) — сделать автоматической проверкой, не полагаться
  на то, что каждый агент вручную вспомнит про `--force`.
