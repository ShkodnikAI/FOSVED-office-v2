## Подключение к dialog_history/dept_activity — что использовано

**Существующие таблицы, только чтение (без миграций):**
- `dialog_history` (FO-006-схема в core InitDB): лента отдела (`/api/depts/<dept>/dialog` — последний chat_id, 50 сообщений), глобальный поиск (`/api/dialog/search`), источник непрочитанных (`MAX(id)` по отделу + COUNT после seen-отметки).
- `dept_activity` (существует для учёта обращений к отделам): порядок кнопок — 30-дневное окно по `last_used_at`, сортировка по `use_count`.
- `DEPT_COLORS`/`DEPT_NAMES` (proxy/core.py): отдаются API-ем (`/api/depts/chat`) — фронт не дублирует палитру.
- Отправка сообщений — **существующие** `/dept/<dept>` → fallback `/chat` (как работало; лентой дополняется оптимистично, реальная запись появится в истории на следующем открытии).

**Зафиксировано:**
- Схема `dept_activity` хранит накопленный `use_count` без помесячной гранулярности — «частота за 30 дней» реализована как фильтр по `last_used_at` ≥ now−30d внутри таблицы + сортировка по `use_count`; помесячный счётчик потребовал бы миграции, которую наряд запрещает.
- Непрочитанные считаются по отметкам фронта (`seen_<dept>` в localStorage → параметр `seen=`) — серверной модели «прочитано» в схеме нет; бейдж для никогда не открывавшихся отделов не показывается (не спамим).
- Голосовой ввод не подключён (прямое требование наряда): STT-интеграция — отдельная задача; в этом наряде — только визуальное поведение кнопки.
- При отправке вложение сейчас передаётся именем файла (существующий контракт `/dept/<dept>`); загрузка содержимого файлов в отдел — вне рамок этого наряда.
